### D311. The keyboard height comes from the visual viewport
- https://developer.mozilla.org/en-US/docs/Web/API/Visual_Viewport_API (read through a copy: https://ligm.univ-eiffel.fr/~forax/MDN/developer.mozilla.org/en-US/docs/Web/API/Visual_Viewport_API.html) — "The visual viewport is the visual portion of a screen excluding on-screen keyboards"; the on-screen keyboard "can shrink the visual viewport" while the layout viewport stays. So the keyboard height is the window height less the visual viewport height and its top offset (under 80 px: the browser bars, not a keyboard).
- https://weblog.west-wind.com/posts/2023/Apr/17/Preventing-iOS-Textbox-Auto-Zooming-and-ViewPort-Sizing and https://css-tricks.com/?p=339455 — iOS Safari zooms in when a field with text under 16 px gets the focus; the fields here are 14 px (`type.body`), so the count works with a zoom too and the text size does not change (no UI change).
- https://drafts.csswg.org/cssom-view/#dom-element-clientheight — the root element's clientHeight is the viewport height without scroll bars: the layout viewport, which a zoom or the keyboard does not change.
- The bottom sheet sits on the keyboard (`bottom` = the height), the sign-in screen gets the same space at its bottom, and a field that gets the focus scrolls into view after `KEYBOARD_SETTLE_MS` (350 ms). When the keyboard closes the height is 0: the screen is as before. A phone build keeps React Native's `KeyboardAvoidingView`.

### D312. Post with no address scrolls to the address field
- https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollIntoView — `block: "center"` puts the element in the middle of its scroll box. Each Post with no address raises a counter, so a second Post scrolls again.

### D313. "Use my current location" is an icon button in the address field
- T9 chose an icon. `glyph.locate` (a target, the common sign of "my location") in an `IconBtn` (`size.iconSmall`) in the field's right slot (`size.fieldSlot` keeps the text clear of it); its accessible name is "Use my current location", and "Finding your location…" shows under the field while it works.
- https://www.w3.org/WAI/WCAG21/Understanding/name-role-value — an icon button needs a name for assistive technology (the label).

### D314. Two sign-in answers: no account, wrong password
- https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html — it asks for one generic message ("Login failed; Invalid user ID or password") so the answer does not tell which accounts exist, and it notes that "the account registration feature should also be taken into consideration". T9 chose two answers for a clean screen: sign-up here already answers "email already registered" (409), and the per-address limit (20 a minute) stays. The 401 has a code: `no_account` -> "No account uses this email." + "Create an account"; `wrong_password` -> "Wrong password." + "Forgot password?"; before a try only "About" shows.

### D315. A stricter email form, any country
- https://lists.whatwg.org/pipermail/commit-watchers-whatwg.org/2012/013749.html — the HTML standard's "valid e-mail address" (the check of `<input type=email>`; https://html.spec.whatwg.org/multipage/input.html#valid-e-mail-address) as a regular expression: the allowed characters before the @ and letters, digits and hyphens in each part of the domain. Added (T9: "more strictly"): the domain has a dot, each part starts and ends with a letter or a digit, and the ending is 2 to 63 letters. name@company.ng, name@school.in and name@yahoo.co.uk pass; name@domain, name@domain.c, spaces and two @ fail. The app and the sign-up service use the same rule. Sign-in and the reset request keep the earlier loose check (`^[^\s@]+@[^\s@]+\.[^\s@]+$`), so an older account still signs in and gets its reset link.
