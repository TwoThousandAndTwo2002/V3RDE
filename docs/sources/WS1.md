### D419. API Gateway holds the socket; the box posts to @connections
- https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-how-to-call-websocket-api-connections.html — `https://{api-id}.execute-api.{region}.amazonaws.com/{stage}/@connections/{connection_id}`: POST "send a callback message to a connected client", DELETE "disconnect the client"; the calls "use IAM authorization" (SigV4); `@` is sent as `%40` and the connection id encoded; a `GoneException` (410) when the client is gone: the box forgets that connection.
- https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-execution-service-websocket-limits-table.html — connection duration "2 hours", idle timeout "10 minutes", frame "32 KB": the app opens a new socket every 9 min (with a new ticket); the box closes a connection after 2 h; a message is under 200 bytes.

### D420. SigV4 and the role's credentials with the standard library
- https://docs.aws.amazon.com/IAM/latest/UserGuide/create-signed-request.html — the canonical request, the string to sign, the signing key (date, region, service, "aws4_request"). `TestSigV4AWSExample` gives the signature of that guide's example (IAM ListUsers, 2015-08-30) exactly. The canonical path is the path as sent, encoded once more (every service but S3).
- https://docs.aws.amazon.com/us_en/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html — IMDSv2 (a PUT for the token, then the role's credentials); "In a container environment, a hop limit of `1` can cause issues": the box needs the PUT response hop limit 2 (an SME step). The credentials are kept until 5 min before they end.

### D421. A one-time ticket, not the cookie, opens the socket
- The WebSocket host is not the app's host, so the browser does not send the session cookie to it. The signed-in app asks `POST /api/push/ticket` (through Caddy, with its cookie): 32 random bytes, good for 60 s, once, at most 8 open per user. The app opens `wss://.../?ticket=...`; the `$connect` integration passes the ticket, the connection id and the Origin to `POST /api/push/connect`. A used, old or unknown ticket: 401, so API Gateway refuses the socket.
- https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html — "Validate the `Origin` header on every handshake. Always use an explicit allowlist of trusted origins": only `V3RDE_PUBLIC_URL` (the app's origin), an exact match. The same guide says "Avoid tokens in URL query strings because they can leak into access logs": the ticket is in the query because the `$connect` route is the only place API Gateway asks the box before it opens the socket; a ticket is good for one connect and 60 s, so a ticket in a log is already used or dead. The SME keeps the query string out of the API Gateway access log format.
- `$connect`, `$disconnect` and `$default` carry a shared secret as `Authorization: Bearer <secret>` (the file `push_secret`, compared in constant time) that only the API Gateway integrations send; the routes answer 403 without it. Not in another header: Caddy's JSON access log keeps the request headers but hides Authorization (and Cookie). A connection id that the box already has is refused (409), so a second connect cannot take another user's socket.
- The web app only: a phone's WebSocket (React Native) sends the WebSocket host as Origin, which the exact Origin check refuses; the phone app keeps its polling.

### D422. Messages carry only a kind, an id and a status
- https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html — treat every message as input to check: the app keeps only kind, id and status strings and drops anything else (`parsePush`).
- `POST /v1/push/notify` is on the unix socket `/sock/push.sock` only (US1): no container on the network and no caller through Caddy can send a message. The app gets `{"kind","id","status"}`; it drops anything else and never shows it: a message only ends the matching poll wait at once, and the app reads the rescue or the touch-up through its usual signed-in route. So a message cannot show data to the wrong person, and a lost message changes nothing.

### D423. Logout and expiry close the socket
- https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-how-to-call-websocket-api-connections.html — DELETE @connections/{id} "disconnect[s] the client".
- Every 30 s the box asks auth again for the session of each connection checked 1 min ago or more (one call per session), so a logout closes the socket in 1 to 1.5 min. Only a clear answer closes it (no cookie, or auth answered 401): when auth gives no answer (a restart, a timeout) the connection stays and is asked at the next sweep. A session that ended gets DELETE @connections, and the connection is forgotten. A connection older than 2 h is closed too. At most 4 connections per user (the oldest is closed). The cookie value is kept in memory only, never logged.

### D424. The polling stays the fallback; the socket must prove that it works
- https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-execution-service-websocket-limits-table.html — idle connection timeout "10 minutes": the ping every minute keeps the socket open.
- The app sends "ping" every minute (the `$default` route, `POST /api/push/ping`); the box answers `{"kind":"pong"}` through @connections for a connection it knows, and closes one it does not know (after a restart of the push service its list is empty), so the app opens a new one. The app counts the socket as working only for 90 s after a pong. So a push that does not work (no credentials, a lost list) never makes the polls slow. The ping also keeps the socket under the 10 min idle limit.
- With a working socket: rescue polls every 5 s (was 1 s) and touch-up every 6 s (was 2 s), and a message ends the wait at once; a message that came while the app read the job is kept (the last 20), so the next wait ends at once. Without one (push off, a failure, an old box, a phone) the waits are as before. A failed ticket, or a socket that closes before its first pong, tries again after 2, 5, 15, then 60 s; the steps start again only after a pong (so sockets that the box closes because the user has too many do not loop). A 404 (push off) stops trying until the next sign-in. Push is off until the SME steps: no `-endpoint`, `-url` or secret = the ticket answers 404.
