# X49o — sources for each decision

Change: X49o (services), the password reset by email link: the two routes of the U9 contract in the auth service, and the mail through Google Workspace SMTP (`auth/reset.go` (new), `auth/reset_test.go` (new), `auth/store.go`, `auth/handler.go`, `auth/auth.go`, `auth/cmd/auth/main.go`, `auth/Dockerfile`, `deploy/docker-compose.yml`, `tools/v3rde_stack.sh`; NEW_WORK.md 83).

T9 (2026-10-31): "reset password does not work". The app has had the reset screens since U9 (`mobile/src/screens/Reset.tsx`), but the auth service had no `/api/auth/reset` routes and no mail sender. T9 chose "SMTP relay", then "Google Workspace" (thehungreeapp.com mail is on Google), and asked for the easiest From address: the Workspace mailbox of the app password itself (no DNS change: the domain already sends through Google).

Own evidence: auth tests 22 -> 32, also with `-race`: the whole flow (202, the mail, a short password refused, 200 with a new session, the old session and the old password refused, a used link refused, only the token hash in the data file), the same answer and no mail for an unknown email, the 30-minute end and a new link that replaces the old one, the per-email limit (429 on the third mail in 15 minutes), 503 when no sender is set up, the mail headers (no header injection), no email, token or password in the logs, and no password on a relay without STARTTLS, the per-address limit and the daily cap, and the rollback when the data file cannot be written. The independent review found: free sign-ups could use up the mailbox quota (now 5 requests an hour per address and 300 mails a day); the file write for a known email made the answer slower than for an unknown one (now the lookup is in the worker, after the answer); a failed save lost the old token in memory (now it is put back); an http link base stopped the service (now only the reset mail is off); an app password with spaces failed (now every space goes); the log showed the password length (now "password set"). All fixed, with tests. Known limits (review re-check): three requests for one email block that email's reset for 15 minutes; the daily cap of 300, once used up, stops the reset mail for everyone until the next UTC day; the queue holds 64 requests, so a large burst drops some.

### D281. The two routes and the token of the U9 contract
- `docs/v3rde_reset_password_brief_2026-10-29.md` (the contract the app was built against): `POST /api/auth/reset` -> 202 `{}` also for an unknown email; `POST /api/auth/reset/confirm` -> 200 user + a new session, or 400 `reset link expired` for an unknown, used or old token.
- https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet — "Return a consistent message for both existent and non-existent accounts"; tokens "Randomly generated using a cryptographically safe algorithm", "Stored securely", "Single use and expire after an appropriate period". Here: 32 bytes from `crypto/rand`, only the SHA-256 in the data file, removed when used, 30 minutes, one token per user.
- The short-password answer keeps the text of sign-up (`password must be at least 8 characters`), not the brief's `password too short`: the app checks the length before it sends and shows its own words, so one text for the same rule is simpler.

### D282. The sender: the Google Workspace SMTP server with an app password
- https://knowledge.workspace.google.com/admin/gmail/send-email-from-a-printer-scanner-or-app — the Gmail SMTP server `smtp.gmail.com`, "port 587 for TLS" (the deploy uses "SSL: port 465", D298), the full Workspace email address and an app password; "The sending limit is 2,000 messages per day". The SMTP relay service (`smtp-relay.gmail.com`) authenticates by IP address and needs an admin setting; it is the fallback if the app password is refused (the page says password sign-in from devices ended on May 1, 2025, so an app password "may not work on all devices"; x49p checks it before the deploy).
- https://support.google.com/accounts/answer/185833 — an app password needs 2-Step Verification; it is made at myaccount.google.com/apppasswords.
- https://pkg.go.dev/net/smtp — `Client.StartTLS`, `PlainAuth` (refuses to send the password without TLS, except to localhost), `Client.Data` (a writer that dot-stuffs). The service also refuses a relay that does not offer STARTTLS, needs TLS 1.2 or later, and has one 20 s deadline for the whole exchange.
- The From address is the mailbox itself, so no SPF or DKIM record changes.

### D283. The mail goes out after the answer; limits per address and per email
- https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet — "Ensure that the time taken for the user response message is uniform"; "rate-limiting on a per-account basis". Here one worker looks up the account, makes the token and sends the mail after the 202 (the answer waits for no lookup, no file write and no relay); both routes have the sign-in limit (20 a minute per address), a reset request also 5 an hour per address, each email at most 3 mails in 15 minutes (the limiter key is a hash, not the address), and the service sends at most 300 mails in one UTC day.
- https://knowledge.workspace.google.com/admin/gmail/send-email-from-a-printer-scanner-or-app — "The sending limit is 2,000 messages per day": the cap of 300 keeps most of it for the mailbox's own mail.

### D284. A reset ends every session; no email, token or password in a log
- https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet — "invalidate the sessions automatically". Here every session of the user ends, then a new session starts for the browser that set the password.
- The brief: logs and events have the user id only. A relay error is logged without the address and the token (`scrub`).
- https://www.rfc-editor.org/rfc/rfc5322#section-3.6 — the message has Date and Message-ID; header values lose CR and LF.
- The link carries the token after "#" (U9), so the browser does not send it to the web server or in a Referer; the Referrer-Policy header of the security assessment (F4) adds a second guard.

### D298. Port 465 (TLS from the first byte), not 587
- x49p on T9's Mac (2026-10-31): smtp.gmail.com port 587 gave no answer (IPv4 and IPv6, 8 s), port 465 and 443 were open; T9 chose "465 everywhere". x49p2 then logged in on 465 with the app password, sent the test mail, and the box answered "220" on 465.
- https://knowledge.workspace.google.com/admin/gmail/send-email-from-a-printer-scanner-or-app — `smtp.gmail.com`, "SSL: port 465", "TLS: port 587".
- https://pkg.go.dev/crypto/tls — `DialWithDialer` makes the TLS connection before the first SMTP byte; https://pkg.go.dev/net/smtp — `NewClient` on that connection, and `PlainAuth` sends the password only on a TLS connection. The service picks TLS from the first byte when the port of `-smtp-addr` is 465, else STARTTLS as before. A test checks both: a TLS relay gets the auth and the message; a plain relay on the TLS port gets no password. The independent review of this change found one minor item, fixed: the dial, the TLS handshake and the exchange now share one deadline (`-smtp-timeout`), so a slow relay cannot take twice as long.
