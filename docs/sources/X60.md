### D352. One PATCH route for the owner's change
- https://datatracker.ietf.org/doc/html/5789 — PATCH "is used to apply partial modifications to a resource"; an error "can be specified with a 409 (Conflict) status code when the request cannot be applied given the state of the resource". `PATCH /api/listings/{id}` takes `{"title", "number_of_serving", "reset"}`, each optional, no other field (`DisallowUnknownFields`); a grabbed listing is 409, an ended listing without `reset` is 409 ("listing expired: send reset to post it again"); the same limits as a new listing (title 1-80 bytes, servings 1-99). Tests: `TestUpdateTitleServingsAndTimer`, `TestUpdateEndedAndGrabbed`.
- https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/ — the owner check is on the server for each object: another user's listing is 404, the same answer as an unknown id (as Delete, X48t), so an id cannot be probed.

### D353. The timer reset is the store's TTL from now; an ended listing comes back only with it
- https://claude.ai/artifact/Ss6HoXmDx4oRbsqfnyyvDy — the approved mockup (version 2): "Reset the timer to 30 minutes", and "Post again" on an ended card ("It shows again for 30 minutes").
- https://datatracker.ietf.org/doc/html/5789 — a partial modification: a field that is not sent stays as it is, so a change without `reset` keeps the time.
- T9: "30 min from now" and "Yes, post again". `reset` sets `expires_at` = now + the store's TTL (30 minutes, `DefaultTTL`); a change without `reset` keeps the time. An ended listing that nobody grabbed changes only with `reset`, and then it is active again and in the feed. A grabbed listing never changes, also with `reset` (T9: "Before a grab only": the receiver counts on the name and the number). The app sends `reset` for an ended listing by itself (`listingChange`), and its popup is "Post again".

### D354. The Facebook post says the change
- https://developers.facebook.com/docs/pages-api/posts — `POST /{page_post_id}` with `message` updates a post (the same call as the [CLAIMED] edit, D83). T9: "Edit the post". After a 200 the listings service calls `PUT /api/fanout/{id}` with the owner's session cookie only, in the background (`ShareHook.Changed`; never for a test account, X44h). Fan-out reads the listing again and edits the post only when its text or its banner changes; a new timer alone changes no text and no Facebook call, but the sweep uses the new time. A post again removes [UNAVAILABLE]. A claimed post never changes (409 before any model call). Tests: `TestUpdateTellsFanout`, `TestFanoutChangeEditsThePost`, `TestFanoutChangeAfterPostAgainAndClaim`.
- https://genai.owasp.org/llmrisk/llm052025-improper-output-handling/ — a new title or number writes the post text again with the same Muse steps and checks as a new post (`writeText`, moved out of `publish`: the model check, no link, not the pickup text), under the same budget caps. The owner's title never goes to Facebook as raw text.

### D355. The last change wins; a reset is never marked [UNAVAILABLE]
- https://datatracker.ietf.org/doc/html/5789 — PATCH "is neither safe nor idempotent", so two changes in a row are two requests. Under the status lock, fan-out reads the listing again: a change whose text was written for older words changes nothing (409 `stale`); the newer change's own call edits the post. The sweep marks a post [UNAVAILABLE] only when its timer still ran out under the lock (a reset between the list of due posts and the edit). A change while the first post is still being published (409 `pending`) is tried again for 145 s (`ChangeBackoff`), longer than the longest share (95 s). Tests: `TestFanoutChangeStaleAndSweepAfterReset`, `TestChangeHookWaitsForThePost`.

### D356. The app: a pencil next to the X
- https://claude.ai/artifact/Ss6HoXmDx4oRbsqfnyyvDy — the mockup T9 approved ("V3RDE Listing Edit Mockup", version 2): a frosted round pencil button next to the Delete X, on every card nobody has grabbed; the Delete popup with the review's title field and servings row, the chip "Reset the timer to 30 minutes", and Keep / Save; on an ended card the title "Post again" and no chip. No new part and no new token. Test: "Give: a pencil next to the X opens the change popup", "listingChange: the owner's change of a posted listing". The new texts are English until the next translation round (`mobile/tests/app_texts.json` has their ids).

Review (independent, 15 minutes at most): four defects, all fixed. (1) An older change that finished after a newer one could put the older words on Facebook: fan-out now reads the listing again under the lock and drops a stale change (D355). (2) A change during the first publish got 409 `pending` and was not tried again: the change hook now tries again on that code (D355). (3) The sweep could mark a post [UNAVAILABLE] just after a reset: the sweep now checks the time under the lock (D355; the delete hook still marks at once). (4) The app called every 409 a grab: an ended listing now says "It ended. Tap the pencil to post it again.". The review found no problem in the owner checks, the grab refusal, the test-account skip or the save rollback.
