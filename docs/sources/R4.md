### D255. The agent: Muse Spark with the built-in web_search tool
- https://dev.meta.ai/resources/blog/build-with-muse-spark — "Meta Model API includes built-in web search grounding: real-time, cited answers with no retrieval stack to build or maintain"; the tool is `{"type": "web_search"}` in the `tools` of a Responses API call, run server-side. So the agent is one Responses call with that tool; no search stack of our own.
- https://www.promptfoo.dev/docs/providers/meta/ — "Web search bills separately ($2.50 per 1,000 queries)". Meta's page gives no price, so this number is from promptfoo; each `web_search_call` item of the answer adds $0.0025 to the call's cost, so the caps count it. Check it against the first real bill.

### D256. When: no place, or a directory failure, and the failure seeds the prompt
- https://feedam.org/api/openapi.json — the directory answers a list of resources for a ZIP or lat/lng; an area with none answers an empty list. Both an empty list and a failure start the search; the prompt says which ("found no places" or "did not answer (…)"), in our own words: the directory's error text is cut to 120 characters, and the pickup text never goes in (only the ZIP or lat/lng).

### D257. Web places are untrusted text: checked, marked, credited
- https://genai.owasp.org/llm01/ — indirect prompt injection: "an LLM accepts input from external sources that can be controlled by an attacker"; "Segregate external content … Separate and denote where untrusted content is being used". The prompt says web text is data; each place must have a name, an address and an https `source_url` (else it is dropped), every text is one line and cut, a website that is not https is dropped, a type not in the list is empty, at most 6. The places carry `source: "web_search"` and the answer's attribution says a web search found them and to check before going. A web place has no email, so `/send` never mails one.

### D258. A job that the app polls
- https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-quotas.html — the HTTP API integration timeout is 30 seconds; a web search can take longer, so `?async=1` answers 202 at once and the job runs up to 90 s; the app polls `GET /api/rescue/{id}` (the scan job pattern, X44b). The photo is read before the 202 (it needs the caller's cookie). One job per listing (the existing mark); a failed job does not block a new one; a job running at a restart becomes `failed` / `interrupted`; independent review: when the final save fails, the job is failed in memory (never left `running`). The one-request route stays as it was for the e2e script: no web search, no `status` or `found_by` field, and 409 while a job for the listing runs (independent review).
