### D331. The size from the header first, then the decode
- https://github.com/golang/go/issues/79063 — the Go team leaves the allocation limit of a decode to the caller. https://pkg.go.dev/image#DecodeConfig — DecodeConfig reads only the header (the width and the height). The analyze route (`server.ReadImage`, used by `/v1/analyze` and `/api/analyze`) and the gate's non-JPEG path read the size first and refuse more than 50,000,000 pixels (the limit the gate's JPEG path and the bundle route already had). A header that cannot be read goes on as before (the decode then fails as before).

### D332. A memory limit for the gate
- https://docs.docker.com/reference/compose-file/services/#mem_limit — the container's memory cap. The gate had none, so one picture could take the box's memory. 1 GB: the largest picture now decoded (50 MP) needs about 750 MB in the non-JPEG path (a 16-bit PNG decodes to 8 bytes a pixel, 400 MB; then an RGBA copy, 200 MB, and the RGB copy, 150 MB). https://pkg.go.dev/runtime/debug#SetMemoryLimit — GOMEMLIMIT (850 MiB, above the about 715 MiB of one 16-bit decode) makes the Go collector work to stay under it; the model's memory is not Go memory and is not measured here (to check on the box with `docker stats`).

### D333. One photo is decoded at a time in the gate
- https://go.dev/ref/spec#Channel_types — the gate's one-place channel (the model slot) is now taken before the decode, not after it. Before, every request decoded at once and only the model call waited, so two 50 MP PNGs at the same time needed about 1.5 GB, more than the 1 GB cap. The queue in front of the slot (8, "busy: gate queue full") is as before; the slot is given back when the request returns (so its decoded photo is not held when the next decode starts), or at once when the decode fails. A test sends a bad photo while another request is in the model: it gets no answer until the first ends; with the slot taken after the decode (the old order) the test fails (a mutation run).

Review (independent, 15 minutes at most): four points, all fixed. (1) Decodes ran in parallel before the queue, so the 1 GB cap was not safe: D333 and GOMEMLIMIT. (2) The 550 MB estimate left out 16-bit PNGs: now about 750 MB (D332). (3) The edge test decoded a 10 x 10 PNG, not 50 megapixels: the gate and server tests now check 8000 x 6250 (passes) and 8000 x 6251 (refused); with ">" changed to ">=" both tests fail (a mutation run). (4) No test showed that a WebP is checked: the inference refusal test sends a WebP header of 16384 x 16384 and gets 413; with the WebP decoder not registered it fails (a mutation run).

Re-check (the same reviewer): the four fixes are correct, no deadlock and no slot leak (the gate tests pass with -race). Three more points, fixed: GOMEMLIMIT was 700 MiB, under one 16-bit decode (now 850 MiB); the slot was given back after the model call while the photo was still held (now at return); no test showed one decode at a time (TestDecodeWaitsForTheSlot).
