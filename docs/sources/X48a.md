# X48a — sources for each decision

Change: X48a, the first part of the speed plan (project doc `docs/v3rde_speed_plan_2026-10-29.md`; NEW_WORK.md 48). T9 2026-10-29: "we need to reduce all latency as much as possible ... single items down to 5-6 seconds and multi items to 10-12 seconds ... make this as parallel as possible".

Own evidence (box, script output, 2026-10-29): the gate took a median 1,071 ms with 1 thread and 595 ms with 2 threads (X45b); SAM median 863 ms (ledger); in the X44i stress run a single photo took 9.1 s at the client (server 5.8 s). The events line had only the length of each call, not its start, so the order of the calls in one scan could not be read from it.

### D197. SAM with the gate, Muse after the gate
- https://pkg.go.dev/context — a value in the request context reaches every call of the run, and a cancel stops them.
- T9's rule (project doc `docs/icarus_x36_handoff_2026-10-28.md`, B4): "start the 3 SAM calls at the same time as the gate; start the paid Muse calls only after the gate passes."
- A `GateBarrier` in the context holds every `muse:` call in `Client.Do` until the gate answers. NOT_FOOD or a gate failure closes it and cancels the run, so a photo that is not food pays at most SAM (3 × $0.0025) and never Muse. The SAM spend of such a photo is in its events line and settles its budget hold.
- The busy slot and the daily cap come first, because SAM is paid and starts with the gate.
- The scan job's progress (X44b) is held until the gate passes and is then sent in order; with NOT_FOOD it is dropped, so the app never shows boxes of a photo that is not food. Found by the cloud preflight: a test saw boxes on a NOT_FOOD job.

### D198. When each call starts
- https://sre.google/sre-book/monitoring-distributed-systems/ — measure the latency of each part to find the slow one.
- Each call has `at_ms` (its start, in ms after the request start) and `wait_ms` (a Muse call's wait for the gate); the event has `gate_at_ms`. A new test with a 300 ms gate shows that every SAM call starts before the gate ends and every Muse call after it.

### D199. One connection pool for the Meta calls
- https://pkg.go.dev/net/http#DefaultMaxIdleConnsPerHost — Go's default transport keeps 2 idle connections per host.
- A scan opens 4 to 7 calls to the Meta API at the same time (3 SAM concepts, the early whole-photo call, the naming chunks). `MetaTransport` keeps up to 32 per host (64 in all, 90 s idle), so the next scan uses open connections and does not wait for a new TLS handshake.

### D200. The live listings are read at the start
- https://go.dev/blog/pipelines — start independent work at once and wait for it where it is used.
- The dedup list (the caller's live listings) is fetched in a goroutine when the scan starts; `dedup()` waits for it. The goroutine writes only its own variables, and `dedup()` copies them into the event, so the race detector run of the package is clean.
