# X32b — sources for each decision

Change: X32b, the app on the one route (X32a): one call to `/api/analyze` with the photo and the phone's barcode; one item = the form as before (the server's photo_id as the listing photo); several = the review list (approved mockup); each error code has its own sheet; uploads at about 2376 px, JPEG 0.9. Approved UI: project doc `docs/icarus_x32_mockup_2026-10-27.md` (mockup artifact version 2, T9 2026-10-27). Read 2026-10-27.

Own evidence: the real app export (not the mockup) ran in Chromium with a fake camera and recorded API answers (Playwright route interception) for the 200 multi-item, the 200 barcode single item and the 7 error answers: no page errors; every listing was posted with `photo_id` and no photo bytes; one forced failure stayed on the list with its error.

### D51. One call; the error code picks the sheet
- https://www.rfc-editor.org/rfc/rfc9110#name-status-codes — the status says what happened; the app reads the `code` in the body to choose among answers that share a status (422 not_food / model_no_food_single / model_no_food_multi).
- T9 2026-10-27: the approved sheets per code (mockup states 6–11); `not_food` and `gate_unavailable` keep the X25 sheet and text.

### D52. Several items: one review list, posted one after the other; a failed item stays
- https://www.nngroup.com/articles/error-message-guidelines/ — keep the user's work when something fails, and say how to fix it.
- T9 2026-10-27 (mockup): title, servings and remove per item; one pickup for all items; "Post N listings"; a failed item stays with its error and the summary "N listings posted. M items are kept here; try again."

### D53. The progress line shows at once
- https://www.nngroup.com/articles/progress-indicators/ — show progress for waits over a few seconds, so people know the system is working.
- Own evidence (the real-app run): inside an animated row the "Posting 3 of 6…" line appeared after the rows' rise delay (about 1 s), so it is a plain line.

### D54. The listing photo is the server's item photo (photo_id)
- https://reactnative.dev/docs/image — an Image source on Android is loaded without the session cookie (X3, READ 2026-10-24: 9/9 `/photo` requests 401), so item photos load through `fetch` as data URIs, as listing photos do (`api.photoUrl`).
- T9 2026-10-27: "the server cuts and stores the crops, and the listing refers to the stored crop".

### D55. Uploads at Muse's image limit: about 2376 px long side, JPEG 0.9
- https://dev.meta.ai/docs/image-understanding — the image token limit that D8/D28 measured (4,096 image tokens = about 2376 × 1337 at 16:9).
- https://docs.expo.dev/versions/latest/sdk/imagemanipulator/ — resize by width keeps the aspect ratio; `compress` is the JPEG quality.
- Decision D28 (X30b, `docs/sources/X30b.md`): "to build in X32"; it also gives the server's item crops more pixels.

### D56. The item photo is a 94 pt square (new token size.thumb)
- https://developer.apple.com/design/human-interface-guidelines/images — supply images for the screen's scale (@3x on current phones): 94 pt needs 282 px.
- T9 2026-10-27: "bump up the thumb to 92-94"; the style guide gets the line in the same change (rule 0).
