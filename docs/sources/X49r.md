### D293. A list answer gives one item for each valid object
- https://datatracker.ietf.org/doc/html/rfc8259 — "A JSON text is a serialized value"; an array is "square brackets surrounding zero or more values", an object "a pair of curly brackets surrounding zero or more name/value pairs". A list of objects is one JSON text; the first '{' to the last '}' of it is not.
- https://dev.meta.ai/docs/image-understanding — the prompt states the fields and asks for JSON; it cannot force one object, and T6 shows the model gives a list on a photo of several products.
- T9 chose "Keep all items": each valid object of the list is an item (`Source` "whole", servings 1, no box: SAM found none, so each item photo is the whole photo), at most `MaxListItems` (12). An invalid object is left out; no valid object is the old error. The list is the first JSON value that starts at a '[' (up to 8 are tried; words around it are ignored); an object `{"items": [...]}` (the shape of the multi-item prompt, `itemFields`) reads the same. Objects with the same name are one item (its count goes up), as `group()` does for boxes. A list that cannot be read falls back to one object (words such as "[1]" before the object). The prompt does not change (`TestPromptBytesArePinned`).

### D294. The event keeps why an answer failed
- https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html — "Which events to log" lists "Input validation failures", output validation failures and application errors; "Data to exclude" lists access tokens, passwords, encryption keys and session values. The model's text holds the item fields only (no key, no token, no session value).
- A failed check keeps the reason and the first `RejectTextMax` (300) bytes of the model's text (cut on a character start); the event keeps at most `RejectLogMax` (5) reasons ("… n more"). Before, the reason was only in memory and T3b/T4 could not show it.

### D295. One message for each cause
- https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch (read through the MDN copy at https://docs.w3cub.com/dom/window/fetch.html) — `fetch()` throws `AbortError` when "the request was aborted due to a call to the AbortController abort() method" (our time limit) and a `TypeError` when "there is a network error (for example, because the device does not have connectivity)". The app now keeps that difference (`CLIENT.offline`, `CLIENT.timeout`) in the error.
- Words (mockup approved): `upstream_error` "The scanner could not read this photo. Try again, or retake it closer"; no connection "No connection. Check your internet, then try again"; no answer in time "No answer in time. Check your internet, then try again"; a lost job "The scan stopped. Try again"; any other 5xx "Something went wrong on our side. Try again"; each ends "— your photo is kept." A 200 with no item: "The scanner found no items in this photo. Retake it closer to the food." Busy, too many photos, food check off and a slow photo keep their words.

### D296. A lost upload is sent again; a slow one is not
- https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch — the network `TypeError` means the request did not get an answer; the same `FormData` can be sent again (https://developer.mozilla.org/en-US/docs/Web/API/FormData).
- Only "no connection" sends again: at most `SEND_TRIES` (3) in all, `SEND_AGAIN_MS` (2 s) apart, inside the 75 s limit, and not after the user went back. A time-out is not sent again: the upload is slow, and a second one would be slower. A request that reached the service before the network failed gets the same job (D297); the rate limit counts each request.

### D297. The same photo of the same user gets the job it already has
- https://datatracker.ietf.org/doc/html/draft-nottingham-httpbis-retry — quotes RFC 7230 6.3.1: "A user agent MUST NOT automatically retry a request with a non-idempotent method unless it has some means to know" that the request semantics are idempotent or that the first request was never applied. A POST that started a scan is not idempotent, so the service makes the second try safe.
- https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch — a network `TypeError` does not prove the request did not reach the service (the connection can drop after the upload).
- `?async=1` with a signed-in user: when a job of the same caller kind and user for the same photo bytes (sha256) and the same barcode read runs, or ended with 200 less than `ScanSameAfter` (10 s: the app's 3 tries are 2 s apart) ago, the service answers 202 with that job (event route `same_scan`, code `same_scan`); no second paid scan, no second daily-cap charge. A failed job is not given again, so "Try again" after a failure starts a new scan; a scan of the same photo later is a new scan (with the already-listed check). Another user, or another caller kind, never gets the job.
