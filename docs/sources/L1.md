# L1 — sources for each decision

Change: L1, the first change on branch `LIF` (lost in translation). The translation quality estimator runs in a container and passes a smoke test (`qe/Dockerfile`, `qe/smoke.sh`, `qe/smoke_input.jsonl`). Nothing else in the repo changes.

### D1. MetricX-24-Hybrid-Large, in QE mode, as the first quality estimator

The translations will come from Muse Spark Open, which returns no log probabilities on our endpoint, so the quality score must come from a separate model. MetricX-24 models are hybrid: one model scores with or without a reference (QE mode). The Large size is the one Google recommends for speed. On the laptop it runs in full precision (fp32, see D9); Google states that the bf16 variants differ by less than 0.001 from the full models. A larger size can run later on a GPU, with its own calibration.

- https://github.com/google-research/metricx
- https://huggingface.co/google/metricx-24-hybrid-large-v2p6-bfloat16
- https://docs.baseten.co/inference/model-apis/overview

### D2. MetricX code pinned to one commit, on Python 3.11, with its own package pins

The repo pins `transformers==4.30.2`, `sentencepiece==0.1.99`, `datasets==2.13.1`. These are older packages, so the image uses Python 3.11, not the newest Python. The clone is pinned to commit `fc4978e` (2024-12-12) so every build uses the same inference code.

- https://github.com/google-research/metricx/blob/main/requirements.txt

### D3. pyarrow 14.0.2

`datasets==2.13.1` uses `pyarrow.PyExtensionType`. Arrow deprecated that class and later removed it, and the unpinned install failed with "module 'pyarrow' has no attribute 'PyExtensionType'". 14.0.2 still has the class; another project fixed the same error with the same pin.

- https://github.com/ray-project/ray/pull/41036
- https://upd.dev/apache/arrow/src/commit/26170b477a790052086805dfa02646a732c60957/python
- https://huggingface.co/spaces/visualisable-ai/api/commit/1680fda2b265cff02c3459aefd194e51ae628d2d

### D4. protobuf 3.20.3

With a new protobuf, loading the mT5 tokenizer failed with "Descriptors cannot be created directly". The error text names the fix: downgrade protobuf to 3.20.x. The linked protobuf notice explains the change.

- https://developers.google.com/protocol-buffers/docs/news/2022-05-06#python-updates

### D5. numpy 1.26.4 and torch 2.1.2

Our choice, not a measured error: versions from the same period as the MetricX pins (D2), instead of the newest torch 2.15. The smoke test (D7) is the check that this set runs.

- https://github.com/google-research/metricx/blob/main/requirements.txt

### D6. A hard memory limit with no swap, in a larger VM

Docker's `--memory` is a hard limit, and `--memory-swap` equal to `--memory` gives the container no swap. The first limit was 6 GB in the 8 GiB Colima VM, next to running containers. A measured run (container memory every second) showed that the fp32 model reaches the 6 GB limit while it loads and is killed before the first prediction (cgroup peak 6,144 MB, exit 137). So the Colima VM was restarted with 12 GiB (the documented way to change an existing VM: stop, then start with new flags), the other containers are stopped (not removed) for this run, and the limit is 10 GB, still with no swap.

- https://docs.docker.com/engine/containers/resource_constraints/
- https://github.com/hftsin/colima

### D7. The smoke test is a pipeline check, not an accuracy measure

Six English to Spanish pairs: three good translations and three bad on purpose (an unrelated sentence, an undertranslation, an untranslated sentence). The check passes when every pair gets one score in MetricX's range, 0 to 25, where lower is better. The order of the scores is printed for a person to look at; it is not used as a quality number. No accuracy is claimed before human labels exist.

- https://github.com/google-research/metricx

### D8. fsspec 2023.9.2

With the newest fsspec, `datasets==2.13.1` failed to read the smoke-test input with "Loading a dataset cached in a LocalFileSystem is not supported". In fsspec 2023.10.0 the local file system's `protocol` changed from the string "file" to a tuple, which older `datasets` versions do not handle. fsspec 2023.9.2 is the version before that change, and it is the fix that users of the same error report.

- https://github.com/huggingface/datasets/issues/6330
- https://huggingface.co/datasets/stanfordnlp/imdb/discussions/7

### D9. Full precision (fp32) on the CPU, not bf16

Root cause of the smoke-test failure "could not create a primitive descriptor for a matmul primitive": a bf16 matrix multiply fails in torch's CPU back end on ARM64. Our test in the image (torch 2.1.2): Linear 1024 to 1024 works in fp32 and fails in bf16; Linear 1024 to 1 works in both, so it is not the known 1-output bug. The VM shows the CPU `bf16` flag, so the cause is the software path, not the hardware. The same error is reported on ARM64 servers with torch 2.0 to 2.3 and with torch 2.8, so a newer torch is not a proven fix. The fix is the fp32 checkpoint of the same model (no code change). `qe/test_qe.py` checks that the smoke test does not use a bf16 checkpoint again.

- https://github.com/pytorch/pytorch/issues/125247
- https://github.com/vllm-project/vllm/issues/24976
- https://github.com/pytorch/pytorch/issues/110149
- https://github.com/google-research/metricx

### D10. Load the model with low_cpu_mem_usage=True (accelerate 0.20.3)

Root cause of the next failure (exit 137, "Killed", right after the tokenizer loaded): MetricX's `predict.py` loads the model with `from_pretrained(path, torch_dtype="auto")`, without `low_cpu_mem_usage`. Then transformers builds the model and loads the full weights into it, which needs about 2x the model size in RAM; with `low_cpu_mem_usage=True` the maximum is about the model size. fp32 Large is about 4.8 GB, so the load needed about 9.6 GB, more than the 6 GB limit (and more than the VM has free), so the kernel killed it (exit 137 is SIGKILL). `qe/run_predict.py` runs Google's `predict.main()` and changes only this one argument, and prints the peak RSS. `low_cpu_mem_usage=True` needs the `accelerate` package; 0.20.3 is the version that projects pin with transformers 4.30.2. A web search found no MetricX-specific report of this; the "Killed while loading" pattern is the common out-of-memory case.

- https://discuss.huggingface.co/t/double-expected-memory-usage/15190
- https://huggingface.co/spaces/nvidia/Plan2Align-NV/blob/main/vecalign/metricx24/predict.py
- https://huggingface.co/spaces/thaitung/OpenAI-speech-to_text
- https://huggingface.co/snorkelai/RedPajama-7B-Chat-Curated/commit/179d92cb9d8eab2ec058d6b1b03893ff7bb418e2
- https://docs.docker.com/engine/containers/resource_constraints/
