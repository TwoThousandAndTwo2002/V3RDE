# X36a — sources for each decision

Change: X36a, the fixes from the independent code review of X35 (#16 to #20, HEAD 8d40eca), done before the X35 services are deployed. Two reviewers who did not write X35 read `post/` and the X35e mobile files against `docs/morpheus/post_api.md`, `docs/sources/X35a.md` to `X35e.md`, and the pattern of `inference/` (the service that already calls Muse Spark and SAM 3.1 live). Decisions by T9, 2026-10-28: "touch up would be placed after asynchronously the inference run, this is just to display the photo"; touch-up input "only a" (photo_id); "lets make it a button"; rescue relay: "No relay send" when the place has no email in the directory; "yes lets move forward with this scope". Read 2026-10-28.

Own evidence (tests, not estimates): every fix has a test that failed or could not exist before it. post tests 46 -> 51 (`-race` clean); mobile tests 31 -> 39.

### D101. Touch-up takes only photo_id: an analyze item photo of the caller, session only
- Prior work, `inference/service.go` (the analyze run): the food gate runs before any paid call ("non-food never reaches the API ($0)"), and `inference/orient.go` makes the photo upright; an item photo from that run has passed both.
- Prior work, `server/guard.go`: "a token in a browser bundle is public" — the analyze bearer token is in the app bundle, so a bearer route would let anyone send any image to the paid calls.
- https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/ — OWASP API4:2023: limit what each call can spend. With only photo_id, every touch-up is a photo that a signed-in donor scanned, inside `-rate-burst`, `-max-in-flight` and the daily cap. The app starts it with a button (T9), not by itself after every scan.

### D102. The rescue relay sends only to the address the directory gives for the place
- https://www.rfc-editor.org/rfc/rfc2505.html — RFC 2505 (BCP 30) section 2: an MTA "MUST be able to restrict unauthorized use as Mail Relay"; section 2.1: relay for known recipients or authorized callers, "Else refuse to Relay". A donor-typed address with the donor's own text made the Icarus sender a relay to any address (review finding 1, proved with a test).
- https://feedam.org/api/openapi.json — the directory has no confirmed email field (X35b D78), so most places have no directory email; for them the donor uses the mailto or tel link (their own mail app), and `/send` answers 409.

### D103. mailto keeps "@" literal
- https://www.rfc-editor.org/rfc/rfc6068.html — RFC 6068 section 2: `addr-spec = local-part "@" domain`; the characters to percent-encode in an addr-spec are the gen-delims "except "@" and ":"". `url.QueryEscape` gave `help%40pantry…`.

### D104. Fan-out: memory is the truth when the store write fails; the Page client has no Timeout of its own
- https://go.dev/src/net/http/client.go — `Client.Timeout`: "The timeout includes connection time, any redirects, and reading the response body"; "The Client cancels requests to the underlying Transport as if the Request's Context ended". So a client Timeout of 25 s ended the upload before the 60 s `PublishTimeout` (review finding 5, proved with a test). Each Graph call now has only its own context.
- https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/ — one share must make one public post. The old rollback removed a post that Facebook had accepted, so a retry posted again (review finding 4, proved with a test). Now the post stays in memory (a retry gets 409 `already_posted`), and `FlushStore` writes the file again every minute, whatever `-sweep` is (a third review of this change found the sweep is off by default).
- Prior work, X35c (`post/fanout.go` Begin/End): a claim while the post is being published now gets 409 `pending` (retry), not 404 (lost); "no post" and "pending" are read under one store lock (`Lookup`), so a publish that ends between two reads cannot turn the answer into 404.

### D105. Voice: at most 2 requests at the same time, checked before the body is read
- Prior work, `inference/service.go`: `MaxInFlight` + 503 `busy` ("the box has 1.9 GiB; a decoded 12 MP photo is about 32 MB"). The same rule for voice: one 60 s upload uses about 11 times its size in memory (review finding 6, a test measured 64 MB for a 5.76 MB input), and the image sets `GOMEMLIMIT=200MiB`.
- https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/ — limit the resources each request can take.

### D106. Speech cost rounds up to the whole second
- https://dev.meta.ai/docs/speech-to-text — "$0.18 per hour of audio, billed in whole seconds" (X35d). A part second is a billed second, so the ledger and the cap round up; they never count less than the bill (999 ms counted $0 before).

### D107. Events lines carry remote_ip and forwarded_ip, as inference
- https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html — OWASP Logging Cheat Sheet, event attributes, "Who": "Source address e.g. user's device/machine identifier, user's IP address".
- Prior work, `inference/events.go` (`RemoteIP`, `ForwardedIP`) and `server/guard.go` `ClientIPs`: the same fields in every post service line, so a caller can be traced (review finding, low).

### D108. The voice clip: one stop, kept by the automatic stop; unmount cancels
- https://react.dev/reference/react/useEffect — "Your cleanup code runs one final time after your component is removed from the page (unmounts)": the hook cancels the clip there, so the microphone does not stay on.
- https://nodejs.org/download/nightly/v24.0.0-nightly20250502c240c03013/docs/api/typescript.html — type stripping errors on features that need transformation, among them "parameter properties", unless `--experimental-transform-types` is passed: `src/clipsession.ts` uses plain fields, so `tests/clipsession.test.mts` runs under the same `--experimental-strip-types` as the other mobile tests.
- Prior work, X35e `src/voicerec.ts`: the timer called `stop()` and dropped its clip (review finding 7). Now the stop is one promise: the timer starts it, and the Stop tap (or `onAutoStop`) gets the same clip. The third review proved with tests that a cancel during the microphone start left it open, and that `onAutoStop` could run after a cancel; the session now has explicit states and a generation number, so a cancel always wins, a start while a clip finishes is busy, and a stop during the start waits for it.
