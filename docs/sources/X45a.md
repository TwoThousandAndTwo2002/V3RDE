# X45a — sources for each decision

Change: X45a, the food gate runs on LiteRT 2.3.0 (`gate/litert.go`, `gate/litert_test.go`, `gate/Dockerfile`, new `gate/cmd/gatebench`; NEW_WORK.md 43). The gate ran on LiteRT 1.4.0 (`libLiteRtRuntimeCApi.so`). On the box its median was 1,134 ms (invoke 1,119 ms) for each photo, and it runs before SAM and Muse, so every scan waits for it.

Own evidence (2026-10-29, cloud x86_64, 2 vCPU, Go 1.24.7, the pinned model `gate_pe_s16_f16w_384.tflite` c0618012… and head 7ba764ea…):
- Parity on all 1,432 gold photos (`gate_gold.jsonl` set), 1.4.0 against 2.3.0, with `gatebench -compare`: 0 verdict flips, largest |dp| 8.3e-6, largest |dy| 1.4e-5, lowest cosine 0.9999999964. Verdicts on 2.3.0: 903 FOOD, 529 NOT_FOOD.
- Speed, the first 100 photos, one run at a time: 1.4.0 1 thread median invoke 1,646 ms (p90 1,761); 2.3.0 1 thread 589 ms (p90 640); 2.3.0 2 threads 339 ms (p90 378); 1.4.0 2 threads 1,496 ms. The box (ARM64) numbers come from the box bench after the deploy (`docker run --entrypoint /gatebench`), not from these.
- The aarch64 `libLiteRt.so` needs GLIBC 2.34 at most (objdump); debian bookworm has 2.36.

### D186. LiteRT 2.3.0 (the newest release) for the gate
- https://pypi.org/project/ai-edge-litert/2.3.0/ — the wheels `ai_edge_litert-2.3.0-cp312-cp312-manylinux_2_27_{x86_64,aarch64}.whl` hold `ai_edge_litert/libLiteRt.so`. `pip index versions ai-edge-litert` (2026-10-29): 2.3.0 is the newest.
- https://github.com/google-ai-edge/LiteRT/releases — the 2.x line changed the C API (v2.1.0: `TensorBuffer::CreateManaged()` always needs an Environment; v2.2.0: XNNPACK CPU changes).
- The sha256 of `libLiteRt.so` is pinned for each CPU type in the Dockerfile: amd64 eec47eb3…, arm64 b57687dc….

### D187. The 2.3.0 C API calls
- https://github.com/google-ai-edge/LiteRT/tree/v2.3.0/litert/c — tag v2.3.0, commit 4352e261. `LiteRtCreateModelFromFile(LiteRtEnvironment, const char*, LiteRtModel*)` takes the environment, so it is made first. `LiteRtLayout.has_strides` is an `unsigned int` bit-field and `sizeof(LiteRtRankedTensorType)` is 72 (litert_model_types.h asserts it; the cgo preamble asserts it too).
- https://github.com/google-ai-edge/LiteRT/blob/v2.3.0/litert/c/options/litert_cpu_options.cc — the CPU options are the opaque option with the identifier `xnnpack` and a TOML payload (`num_threads = N`). `LrtCreateCpuOptions` is not exported by `libLiteRt.so` (nm), so the gate makes the same option with the exported `LiteRtCreateOpaqueOptions` and `free` as the destructor. The new test shows that 2 threads give the same output as 1, and that a count out of 1..8 is refused.

### D188. One tool for parity and speed
- https://docs.docker.com/reference/cli/docker/container/run/ — `--entrypoint` runs another binary of the same image, so the bench uses the deployed library and model code.
- A runtime change is checked by its output on the same 1,432 inputs, not by its version number.
- `gatebench` scores a folder exactly as the service does (Decode, TensorFor, Embed, Head.Verdict) and writes one line per photo; `-compare` gives the verdict flips (exit 1 when there is one). It is in the image as `/gatebench`, so the box bench and the int8 check (next change) use the same code.

### D189. The service keeps 1 thread until the box bench
- https://aws.amazon.com/ec2/instance-types/t4/ — t4g.small has 2 vCPU and 2 GiB. The gate runs while SAM and the Muse calls run, so 2 gate threads can slow the rest. The compose file keeps `-threads 1`; the box bench (1 against 2 threads, with and without load) decides.
