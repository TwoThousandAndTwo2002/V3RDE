# X38d — sources for each decision

Change: X38d, the barcode lookup (`barcode/`) written new for V3RDE (NEW_WORK.md 27). Decisions by T9, 2026-10-28: rebuild the parts that existed before the Hackathon as new code ("b"), "yes continue with barcode". Read 2026-10-28.

Own evidence (2026-10-28, Go 1.24.7): an independent review (an agent that did not write the code) sent 39,002 inputs to the old and the new code (random strings with digits, spaces, dashes and other scripts' digits, valid codes, long codes; every function, and the HTTP routes with GET, POST, HEAD and PUT, good and bad trace ids, a loaded and a failed catalog) and compared the answers and the events lines byte for byte (ids and times masked): no difference. Its test findings are fixed (a test of the pin check, a test of the exact JSON of the answer, the SQLite refusals). Behaviour that the old service also has and that this change keeps: the events file of a day is chosen at write time, a 405 has no Allow header. The 15 tests of the barcode service that the app used before the Hackathon (14 without the `sqlite` tag, 1 with it) pass on the new code (not committed). The module `github.com/mattn/go-sqlite3` v1.14.52 was taken from its GitHub tag and zipped with Go's own module zip format; its `h1:` hash is the one in `go.sum`, so it is the same code.

### D136. Write the service new; keep its answer, its outcomes and its catalog
- https://gs1.org/how-calculate-check-digit-manually — the GS1 check digit: "Multiply value of each position by" x3, x1, x3, …; "Add results together to create sum"; "Subtract the sum from nearest equal or higher multiple of ten = Check Digit". The test codes have check digits computed by this rule with a short Python check.
- The route, the JSON of the answer (the inference service reads `outcome`, `admissible`, `product`), the four outcomes, the `why` texts, the healthz counters and the events line are kept. The catalog file is not in V3RDE: the service reads it from a read-only mount and refuses any file whose sha256 is not the pin or whose row count is not 374,760, as before; then every lookup answers UNAVAILABLE (it fails closed).

### D137. The catalog is opened read-only and immutable
- https://sqlite.org/uri.html — "The mode query parameter determines if the new database is opened read-only"; "The immutable query parameter is a boolean that signals to SQLite that the underlying database file is held on read-only".
- https://www.sqlite.org/pragma.html#pragma_query_only — the driver's `_query_only` (go-sqlite3 README: "For more information see PRAGMA query_only"). A test checks that a DELETE fails.

### D138. SQLite is linked statically, and its tests run in the image build
- https://github.com/mattn/go-sqlite3 — the driver is cgo; the image builds it against musl with `-linkmode external -extldflags -static`, so the final image is `scratch` (no shell, no libc), as before.
- https://docs.docker.com/build/cache/invalidation/ — the tests with the `sqlite` tag run before `ARG BUILD`, so a new commit with the same code does not run them again.
