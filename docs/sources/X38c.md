# X38c — sources for each decision

Change: X38c, the sign-in service (`auth/`) written new for V3RDE (NEW_WORK.md 26). Decisions by T9, 2026-10-28: rebuild the parts that existed before the Hackathon as new code ("b"), "yes proceed with auth". Read 2026-10-28.

Own evidence (2026-10-28, Go 1.24.7): an independent security review (an agent that did not write the code) sent the same 21 requests to the old and the new service (status codes, bodies, Set-Cookie lines, the rate limit) and found no difference; a data file of the old service opens in the new one and its account logs in. The 10 tests of the old service pass on the new code (not committed). The review found three weaknesses of the password check that the old service also had; they are fixed before this commit (D133). One more (D135) is for the deploy change.

### D131. Write the service new; keep its routes, cookie, data file and hash format
- https://pkg.go.dev/net/http@go1.24.7#Cookie — the session cookie keeps its name (`morpheus_session`: listings reads it) and its attributes: HttpOnly, Secure (unless `-cookie-secure=false`), SameSite=Lax, Path=/, 7 days.
- The routes, the status codes, the error texts, `auth.json` (users, emails, sessions) and the stored password form are kept: the accounts on the data volume must keep working. A test logs in with a data file written by the old service, and with its session cookie.

### D132. Passwords: PBKDF2-HMAC-SHA256, 600,000 iterations
- https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#pbkdf2 — "PBKDF2-HMAC-SHA256: 600,000 iterations (recommended)".
- https://pkg.go.dev/crypto/pbkdf2@go1.24.7#Key — the standard library function (Go 1.24). A test checks it against the RFC 7914 vector (https://www.rfc-editor.org/rfc/rfc7914, section 11: P="Password", S="NaCl", c=80000, dkLen=64), also computed with Python's `hashlib.pbkdf2_hmac` on 2026-10-28.

### D133. A damaged stored hash is never a match, and takes the same time
- https://pkg.go.dev/crypto/hmac@go1.24.7#Equal — the keys are compared in constant time.
- The review found that a stored hash with a short key let wrong passwords match (a 1-byte key matched 4 of 2000), that a very high iteration count made one login take 30 s, and that a damaged hash answered at once (so the time showed which accounts had one). Now the key must be 32 bytes, the salt at least 16, the iterations 1,000 to 6,000,000; any other form is no match after a check against the dummy hash. The hashes the service makes (32-byte key, 16-byte salt, 600,000) are not changed.

### D134. An unknown email costs the same time as a wrong password
- https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-responses — the application "must respond with a generic error message regardless of whether" the user ID or the password was wrong. The login answer is the same text for both, and an unknown email is checked against a dummy hash of the same cost, as before.

### D135. Open item: the rate-limit address comes from a header the caller can set
- https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults — Caddy "sets or augments" `X-Forwarded-For` and by default ignores the values a caller sent, "to prevent spoofing"; other headers, such as `CF-Connecting-IP`, are passed on unchanged.
- The review found that a caller who sends a new `CF-Connecting-IP` (or `X-Forwarded-For` when the service is reached without Caddy) gets a new budget for each request. The old services (analyze, auth) do the same. The fix belongs in the deploy change (Caddy sets the one address header the services read); it is not in this change, so the wire behaviour stays the same.
