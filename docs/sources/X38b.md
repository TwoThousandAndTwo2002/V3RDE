# X38b — sources for each decision

Change: X38b, the listings service (`listings/`) written new for V3RDE (NEW_WORK.md 25). Decisions by T9, 2026-10-28: rebuild the parts that existed before the Hackathon as new code ("b"), "okay lets goi with your plan depicted in the table", "okay never mind lets move on". Read 2026-10-28.

Own evidence (2026-10-28, Go 1.24.7): an independent review (an agent that did not write the code) compared the old and the new service: the exported API (`go doc -all`), about 45 requests one by one (status, headers, bodies), the data file read both ways (old -> new, new -> old) and the events lines. It found no other difference than D125 and D126; its findings are fixed before this commit (D125, D130, the tests). The 15 tests of the listings service that the app used before the Hackathon (with the Hackathon claim hook and the touch-up photos of entry 22) pass on the new code (not committed). The post services (51 tests) pass on the new code with no change to their files; they did not build in V3RDE before this change.

### D123. Write the service new; keep its routes, its JSON and its data file
- https://pkg.go.dev/net/http@go1.24.7#ServeMux — the method and wildcard patterns ("POST /api/listings/{id}/grab", `Request.PathValue`) of the routes.
- The routes, the status codes, the error texts, the JSON of a listing and the format of `listings.json` (id -> listing + `photo_file`) are kept: the app reads them, and the data volume on the box already holds files in this format.

### D124. A photo_id gets one answer for "not yours" and "not there"
- https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/ — "check if the logged-in user has access to perform the requested action on the record". The item photo and the touch-up photo are read only when their `.json` names the same photo_id and the caller as the user; every other case answers 400 "photo_id not found".

### D125. Files are written through a temp file, a sync and a rename
- https://pkg.go.dev/os@go1.24.7#File.Sync — "Sync commits the current contents of the file to stable storage."
- https://pkg.go.dev/os@go1.24.7#Rename — the rename puts the new file in place of the old one, so a crash leaves the old file or the new one. The data file was already written like this; the photo now is too (before, a crash during the write could leave half a photo).
- The review found that a failed rename left the temp file, and that the error text named the temp file. Now every failure removes the temp file, the error names the photo file, and the start removes temp files that a crash left.

### D126. A grab that is not written changes nothing
- https://pkg.go.dev/sync@go1.24.7#Mutex — the store holds one lock for the check, the change and the write. When the write fails, the record in memory is put back, so the answer (500 "could not grab") and the data agree, and the listing can be grabbed when the disk is back. Before, the memory said "collected" and the file did not.

### D127. The claim hook keeps its rules
- https://pkg.go.dev/net/http@go1.24.7#Client — one client with a 30 s timeout; no answer is an error and is tried again.
- Kept from entry 22: tries again on no answer, 409, 429 and 5xx other than 503; at most 7 tries with waits of 2, 5, 10, 20, 40 and 60 s (137 s, longer than the longest share, 95 s).

### D128. The events line keeps its shape
- https://pkg.go.dev/net/http@go1.24.7#Request — "Pattern is the [ServeMux] pattern that matched the request." The line has the pattern, never the path or the query, so no listing id or user id is in the log.

### D129. The image fills a new volume with the service user as the owner
- https://docs.docker.com/engine/storage/volumes/#mounting-a-volume-over-existing-data — "these files or directories are propagated (copied) into the volume by default." `/data` and `/events` are in the image, owned by user 65534, as before.

### D130. The newest listing is first by its time, not by its text
- https://pkg.go.dev/time@go1.24.7#pkg-constants — `RFC3339Nano = "2006-01-02T15:04:05.999999999Z07:00"`: the 9s drop the zeros at the end, so "…:57.52Z" sorts after "…:57.521569942Z" as text. The review found this (also in the old service); the store now compares the parsed time, with the id as the tie-break, so a page cursor is still stable.
