### D169. Polling, not a stream
- https://docs.aws.amazon.com/apigateway/latest/developerguide/response-transfer-mode.html — "Response streaming is only supported for REST APIs."
- The public name is the API Gateway HTTP API `u91rfqqg20` (30 s per request). So the scan answers 202 with a `scan_id` at once, and the app asks again about once a second. Each poll is a short request. The 200 route stays as it is for the callers that use it.

### D170. The boxes as soon as SAM is done, then the names of each chunk
- https://ai.meta.com/research/publications/sam-3-segment-anything-with-concepts/ — SAM 3 finds every instance of a concept ("food") in the image; that is the first answer of the scan (the boxes), before any name.
- In the X32c probe the SAM calls end at about 3 s and the naming calls at about 8 to 9 s, and the three naming calls end at different times. So the job shows the boxes first, then each call's names as it ends. The engine reports through the request context (`WithProgress`), so a scan without a job does nothing new. The names are hints: the review list still uses only the final answer (items grouped, each with its photo).

### D171. The job's answer is the 200 route's body
- https://pkg.go.dev/net/http#Request.Clone — "Clone returns a deep copy of r with its context changed to ctx."
- The scan after the photo runs the same code as the 200 route, with a writer that keeps the body; the request is cloned with `context.WithoutCancel`, so the 202 that ends the client's request does not stop the scan. Every exit (refusals, the cap, a timeout) is the same body and code as on the 200 route, in `answer` with `http_status`. The time limit stays 25 s.

### D172. Only the caller that started it, and not for ever
- https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/ — "check if the logged-in user has access to perform the requested action on the record."
- The `scan_id` is 16 bytes from `crypto/rand` (the photo id code). A GET must be the same kind of caller (session or token) and the same user; anything else gets the same 404 as an unknown id. A finished job is kept 10 minutes, and the service holds at most 64 jobs (the oldest finished job goes first; with 64 running jobs a new one gets 503 `busy`), so the jobs cannot fill the memory of the 2 GiB box.
