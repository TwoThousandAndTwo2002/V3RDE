### D24. Turn every photo upright from its EXIF orientation first
- https://developer.apple.com/documentation/imageio/cgimagepropertyorientation — iOS writes the TIFF/Exif orientation values 1–8; an iPhone held upright writes "right" (6).
- https://developer.android.com/reference/android/media/ExifInterface — Android writes the same tag (`TAG_ORIENTATION`).
- https://jpegclub.org/exif_orientation.html — the 8 transforms.
- https://golang.org/issue/4341 — Go's image decoder ignores the orientation.
- https://hackernoon.com/uploading-jpg-files-on-mobile-with-orientation-size-and-format-traps-a-quick-guide — fix orientation on the server: "Server-side normalisation catches every client you don't control".
- Own evidence: 11 of 20 phone photos had orientation 6 or 3; `orient_test.go` (all 8 values, both byte orders; checked against Pillow `exif_transpose` on real photos).

### D25. Pet food is not food; a photo with only not-food products is an answer
- https://pair.withgoogle.com/chapter/errors-failing/ — Google PAIR, *Errors + Graceful Failure*: tell the user what happened and let them act ("Add anyway").
- Own evidence: X30b photo 1 (24 pet-food boxes, all correctly `food: false`, but the run ended with "no item passed the contract"); T9 decision 2026-10-27.

### D26. The probe runs photos at the same time; SAM is paid once per photo and concept
- https://dev.meta.ai/docs/pricing-rate-limits — 3,000 requests per minute (a 20-photo run uses about 200).
- https://go.dev/doc/effective_go#concurrency — goroutines, channels as semaphores.
- https://pkg.go.dev/golang.org/x/sync/singleflight — the "one call, others wait" pattern used for the SAM cache.
- Own evidence: `TestSAMCacheOneCallUnderConcurrency` (8 runs of one photo at the same time, 1 SAM call).

### D27. The SUP runs its S3 checks at the same time (template v3)
- https://docs.python.org/3/library/concurrent.futures.html — `ThreadPoolExecutor` for independent subprocesses.
- https://go.dev/doc/effective_go#concurrency — the same principle in the engine (D21).

### D28. The app uploads at Muse's limit: about 2376 px long side, JPEG 0.9 (to build in X32)
- https://dev.meta.ai/docs/image-understanding — image cost scales with resolution; the model may resize.
- https://www.mdpi.com/1424-8220/22/3/1104 — Gandor & Nalepa 2022: small objects lose detection first under compression.
- https://docs.expo.dev/versions/latest/sdk/imagemanipulator.md — `compress` 0–1 (1 = highest quality) and `resize` in the app.
- Own evidence: `x30b_hand_check.json` (1600 px / 0.85: 95.4% vs 99.4%; bananas 71 counted vs 1; small salad labels 17/23 vs 23/24); D8 (4,096 image tokens = 2376 × 1337 at 16:9).
