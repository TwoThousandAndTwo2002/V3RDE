### D401. A prompt registry: id, version, and the sha of a golden text
- https://pkg.go.dev/crypto/sha256 — `sha256.Sum256` (FIPS 180-4 SHA-256). The pin is the first 64 bits (16 hex characters).
- https://csrc.nist.gov/pubs/sp/800/107/r1/final — NIST SP 800-107 Rev. 1, section 5.1: a hash value may be truncated to its leftmost bits for an application. Here it tells a few dozen prompt texts apart; it is not a security control.
- Each module has a list of the prompts it sends (`inference/prompts.go`, `post/prompts.go`): id, version, the call purposes, and a Golden function. A prompt made from parts (MultiPrompt, NamePrompt, DetailPrompt) is rendered with two fixed boxes in all three box introductions (coordinates; marks and coordinates; marks only), so a change in any branch changes the sha. A template with `%s` (RescuePrompt and others) is pinned as the template.
- The rescue goldens render the template for a fixed listing with no scanner note and with the note of each meal_condition (`hintWords`, the description part), so the words of the note are pinned too. The transcribe pin is the JSON of the fixed request fields that `Transcribe` sends (`transcribeFields`).
- `TestPromptPins` in each module checks the registry against a pin history, `prompts_pins.txt` (`analyze.CheckPinHistory`): one row "id version sha" per prompt version; one sha for each id and version; the current text is the newest row of its id. A change of a prompt's text fails the SUP until it adds a new row with a new version; the version in the logs then changes with the text. The file only gets new rows: the generator of the SUP apply script refuses a change whose new `prompts_pins.txt` does not start with the old one (an edited row would let one version name two texts).

### D402. The prompt is found by the purpose and the text sent
- https://dev.meta.ai/docs/protocols/responses — the text parts of a request are `input_text` items: the Match reads them (TextOf), so the prompt is known from what was sent, not from a guess.
- Two prompts share one purpose: `rescue:draft` (R3: email or drop-off) and `touchup:edit` (light or background). A spec can have a Match on the text sent: `StartsWith` (the template up to its first `%`, so the scanner note does not change the answer), `EndsWith` (compactRule), or an exact text (the edit modes, BiggerPrompt). When no spec of the longest purpose fits, the next shorter purpose is tried: a SAM concept named "box" (an item title in the touch-up) is `sam.concept`, not `sam.box` (whose Match is the `<0f>1` token). A text that no spec matches logs `prompt_id: "unknown"`.
- Tests: `TestPromptPurposes` (each purpose, both rescue prompts with and without the scanner note); `TestPromptEveryPurposeInCode` (every purpose literal in the code has a spec); the flow tests of inference (`purposes()` in `engine_test.go`) now fail on a call with an unknown prompt.

- The auto touch-up job keeps its calls (`inference.WithCallLog`: `Client.Do` and `EditJSON` add each call to the log of the context) and writes them on its line (`calls`, `post/touchup.go` `v2Calls`); `TestTouchupV2Background` checks `touchup.bigger`, `sam.concept` and `sam.box` there and no `unknown`.

### D403. input_sha is the sha of the text that was sent
- https://dev.meta.ai/docs/protocols/responses — the Responses request: `input` is a list of messages whose content parts are `input_text` (`text`) and `input_image`. `TextOf` takes every `text` string in order (images are not in it), and `input_sha` is its sha. Two calls with one prompt version but other parts (the box list, the scanner note, the voice rule, the transcribe keywords) have other input_sha values.

### D404. Each call line has the effort, the API id and the cached tokens
- https://dev.meta.ai/docs/reasoning — `reasoning.effort` changes how the model answers, so it is logged per call (`effort`, as sent; "" = the API default; SAM calls send none). It is set before the wait for the food gate, so a call that the gate stops has its effort too.
- https://dev.meta.ai/docs/prompt-caching — cached input tokens are billed at a lower rate; `cached_tokens` and the API's response id (`api_request_id`) were in `Call` and now reach the event line.
- https://pkg.go.dev/encoding/json#Marshal — "Anonymous struct fields are usually marshaled as if their inner exported fields were fields in the outer struct": `PromptRef` is embedded, so the line has `prompt_id`, `prompt_version`, `prompt_sha` next to `purpose` (`TestPromptRefJSON`).

### D405. The analyze event line keeps the engine settings
- https://developers.google.com/machine-learning/guides/rules-of-ml/ — Rule #29: "save the set of features used at serving time": the settings of the engine are a part of what made the answer.
- A change of a flag (split, compact, marks, efforts, size levels, concepts) changes the result without a prompt change; `settings` on each analyze line lets the report tell the two apart. No key and no URL is in it (`TestEngineSettingsInEvent`).

### D406. No prompt text changes
- https://go.dev/ref/spec#Constant_expressions — a string constant made with `+` of constants is one constant with the same bytes, so the named SAM tokens send the same text.
- The SAM prompt tokens of touch-up v2 are now named constants (`SAMObject1`, `SAMBoxFormat`, `SAMPointFormat`) with the same bytes, so the registry can pin them. All earlier tests pass unchanged; `TestPromptBytesArePinned` (server) still pins analyze.Prompt.
