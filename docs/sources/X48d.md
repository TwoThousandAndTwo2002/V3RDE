### D204. Store the details now; show them after a mockup
- T9's words above: storing is the first choice; "ideally we should display it". The display is a UI change, and UI changes need a to-scale mockup first (the UI handoff rule), so this change stores only. The data is then there for the display and for the self-improvement pipeline.
- Keeping the prompt as it is: https://github.com/TwoThousandAndTwo2002/Icarus/blob/services/server/contract.go keeps the contract prompt "byte for byte: the contract tests and the eval results depend on this exact text". A shorter prompt would need a new eval; storing needs none.

### D205. One optional field, a fixed list of keys, each value checked
- https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization/ — "Allow changes only to the object's properties that should be updated by the client." and "avoid using functions that automatically bind a client's input into code variables, internal objects, or object properties".
- So `details` is decoded into its own struct with `DisallowUnknownFields`: a caller cannot set `owner_id`, `status` or any other listing field through it. Every value has a type and a range (the same enums as the contract), the field is at most 1 KB and the description at most 200 characters.
- The app sends only values that pass the same rules (`logic.itemDetails`), so a strange model answer never stops a post. The listing JSON and the data file of a listing with no details do not change (`omitempty`), so the old app and the old data work.
