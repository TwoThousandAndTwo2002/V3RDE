### D247. The scanner's field is a hint, not the decision
- https://www.fsis.usda.gov/es/node/3296 — USDA FSIS, "Shelf-Stable Food Safety": "Not all canned goods are shelf stable. Some canned food, such as some canned ham and seafood, are not safe at room temperature. These will be labeled \"Keep Refrigerated.\"" So `sealed` cannot map to "food bank" by itself. Muse Spark sees the photo (the label) and keeps the rule of X35b: `shelf_stable` is true only for sealed food that keeps without a refrigerator.
- The events line keeps `detail.hint` next to `detail.shelf_stable` (also on a failed draft or directory call: independent review), so the self-improvement step (F6) can count where the scanner and Muse differ. No answer field changes, so the app does not change for R1.
- Option C (a new `perishable` field in the scan) was not taken: the scan prompt is kept byte for byte (`server/contract.go`) and `/v1/analyze` must not change (the other submission uses it).

### D248. The note is marked as the scanner's, on its own line, one line, at most 200 characters
- https://genai.owasp.org/llm01/ — OWASP LLM01 (prompt injection): "Segregate external content from user prompts. Separate and denote where untrusted content is being used." The description comes from the scan of the listing, so the note says where it comes from and that it can be wrong. Control and format characters (new lines, and bidi or zero-width marks: Unicode Cc and Cf; independent review) become spaces, so the note cannot add lines or hide text in the prompt; it is cut at 200 characters (runes), the listings service's own limit (`listings/details.go`).
- https://pkg.go.dev/fmt — the note goes into the prompt as a `%s` argument, so a `%` in the description stays text (a test checks "5% fat" and that no `%!` is in the prompt).

### D249. A listing without the field gets the old prompt; the decode stays loose
- https://pkg.go.dev/encoding/json — "unknown keys in the JSON object are ignored"; a null or absent pointer stays nil. `Listing.Details` is a pointer with `omitempty`, and `ListingDetails` decodes only the two fields rescue uses, so a listing from before X48d, or one with more fields, decodes as before. A test decodes the listings service's own `listings.Listing` type, so a change there that breaks rescue fails in `post`.
- A value that is not in the contract (for example `frozen`) gives no note: the same prompt as before (test).

### D250. The hint only for a vision scan, from the scan's own events line
- Independent review: a barcode answer's `meal_condition` is a fixed value (`barcode/product.go`: `Complete` sets `ready_to_eat`, `Provenance` tags it `constant`), and listings posted before R2 keep it. T9 (2026-10-30): "i thought that we were recording what route a transaction was routed through." It is: each analyze events line has `request_id`, `status`, `user_id` and `source` (`barcode` | `vision`; `inference/events.go`, set in `inference/service.go`), and the listing keeps the scan's `request_id`. Rescue reads that line, read-only, as the touch-up service already reads the analyze events (X48o, `ItemScanNear`), and gives the hint only when `source` is `vision`.
- https://genai.owasp.org/llm01/ — "Segregate external content ... Separate and denote where untrusted content is being used": the `request_id` of a listing comes from the app, so the line must also be the owner's (`user_id`), status 200 with a route (a label report is 204 and names none); anything else gives no hint. Only the listing's UTC day and the day before are read (a scan comes before its post), not the whole history.
- https://pkg.go.dev/encoding/json — the line is decoded into four fields only; "unknown keys in the JSON object are ignored".
