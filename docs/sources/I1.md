### D316. The app reads every code of the still photo
- https://developer.mozilla.org/docs/Web/API/BarcodeDetector/detect — `detect()` "fulfills with an array of DetectedBarcode objects", each with `rawValue` and a `boundingBox` "aligned with the image". So one still gives every code and where it is.
- `mobile/node_modules/expo-camera/build/ExpoCameraManager.web.js` (expo-camera 58.0.14) — `scanFromURLAsync(url, barcodeTypes)` fetches the image, makes an ImageBitmap and runs the same reader as the live camera (`WebBarcodeScanner.detect`), so the app keeps one reader and the same retail types (EAN-13, EAN-8, UPC-A, UPC-E).
- https://tessl.io/registry/tessl/npm-expo-camera/files/docs/barcode-scanning.md — `scanFromURLAsync(url, barcodeTypes?): Promise<BarcodeScanningResult[]>`; "On iOS, only QR codes are supported for URL scanning". The app is a web app for now (T9, Oct 30); on a phone build with no reader, the scan is as today (the live code only).
- "Use photo" waits while the codes are read ("Reading the barcodes"), so the codes go with the photo; at most 2 s (`READ_WAIT_MS`), then the photo goes with no codes.

### D317. The box goes in the still's pixels with the still's size
- https://developer.mozilla.org/docs/Web/API/Window/createImageBitmap — the bitmap is made from the image; the box is in its pixels. The app sends the size of the same image (`fw`, `fh`, from `Image.getSize`), and the service scales the box centre to the scanner's frame (`centreIn`). The upload can be smaller than the still (the app shrinks it), so pixels alone would not match.
- A box that is not inside the still goes with no box: that code becomes an item, but it is matched to no box of the scanner.

### D318. Every code is looked up at the same time
- https://pkg.go.dev/sync#WaitGroup — the lookups run in goroutines and the scan waits for all; at most 8 at a time (a channel as a counter), so 24 codes do not open 24 connections to the barcode service.
- https://pkg.go.dev/context#WithTimeout — all the lookups of a scan share one 3 s budget, and they run while the food check and SAM run, so a slow barcode service cannot make the scan longer than its limit.
- https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/ — the input has limits: at most 24 codes, at most 8 KiB of JSON, only codes of 8, 12, 13 or 14 digits.
- https://www.gs1.org/standards/barcodes/ean-upc — EAN-8, UPC-A (12), EAN-13 and GTIN-14 are the retail lengths (the app's `barcodeOf` uses the same).

### D319. Barcodes + vision: a box that holds a code is that product
- T9 chose "Barcodes + vision". The scanner (SAM 3.1 boxes, Muse Spark names) still runs on a photo with codes, so food with no barcode in the same photo is found too.
- https://dev.meta.ai/docs/sam/segmenting — SAM answers a box for each instance. The smallest box that holds the centre of a code that the catalog knows is that product (a bag or a tray around it stays its own item): the scanner's item for that box is not listed (the ledger box shows the catalog item's number), and the product's photo is a crop of that box when there is no stock photo.

### D320. The barcode items answer when the scanner cannot
- https://sre.google/sre-book/addressing-cascading-failures/ — "graceful degradation": give a smaller answer instead of none. The catalog needs no model, so a busy scanner, the daily limit (`CAPTURE.pausedLine` already says "A barcode still works"), a photo the food check refuses, a time out or no food named still give the barcode items. With no catalog hit the errors are as before. The events line keeps why the scanner did not answer.

### D321. A catalog item in a mixed answer says so
- https://pkg.go.dev/encoding/json#Marshal — with `omitempty` an empty field is left out, so the answers of today do not change. An item that came from a code has `"source": "barcode"`; the app keeps no `meal_condition` for it (a fixed catalog value, R2), as for a barcode answer. The answer's own `source` stays `barcode` or `vision`, so the rescue reads the events line as before.
