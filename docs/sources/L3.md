# L3 sources: one English source file and the language list

### D1. The extractor reads the `ui` app code from git at one pinned commit
LIF must not change `ui`, and the text must come from one known version of the app. The extractor reads `mobile/src` at the commit in `i18n/source.json` with `git ls-tree` and one `git cat-file --batch`, so nothing is copied into LIF and the result can be made again.
Source: https://git-scm.com/docs/git-cat-file

### D2. A message is the whole line, joined parts become placeholders
Text that the app joins with `+` (`"Item " + n + ": " + title`) is kept as one message with placeholders (`Item {n}: {title}`), because a translator must control the word order, punctuation and spaces of the whole line.
Source: https://learn.microsoft.com/it-it/globalization/internationalization/concatenation

### D3. Every string of the app is in en.json or in skipped.json, with a rule
The extractor sorts all string and template literals. A literal that is not text gets a named rule; the cases a rule cannot decide are in `rules.json` with a reason, and an entry that matches nothing is an error. A test makes the two files again from the pinned commit and compares them byte for byte, so a new string on `ui` cannot be lost without a visible change. Test inputs live in `testdata/`, which the go tool ignores as a package.
Source: https://pkg.go.dev/cmd/go#hdr-Test_packages

### D4. Plural parts are marked, not fixed here
`plural(n, "item found", "items found")` gives parts, not lines. Plural forms differ by language (Arabic has six categories, Chinese one), so whole messages with per-language plural forms are needed. This is a change to the app on `ui`; L3 marks these messages with `"arg": "plural"`.
Source: https://www.unicode.org/cldr/charts/latest/supplemental/language_plural_rules.html

### D5. Language tags (BCP 47)
`es-419` is the registered tag for Spanish of Latin America as a whole, not one country. `zh-Hans` uses the script subtag for Simplified Chinese. `ar-001` is Modern Standard Arabic in ICU/CLDR (Arabic with the region "World").
Source: https://www.rfc-editor.org/rfc/rfc5646
Source: https://www.alvestrand.no/pipermail/ietf-languages/2005-July/003538.html
Source: https://www.localeplanet.com/icu/ar_001/

### D6. Native names, scripts and direction
Native names: `español (Latinoamérica)` (shortened from `español (Latinoamérica y el Caribe)`), `português (Brasil)`, `中文（简体）`, `हिन्दी` (Devanagari, left to right), `العربية` (right to left). Script codes are ISO 15924 (`Latn`, `Hans`, `Deva`, `Arab`). A test checks that each native name is written in its own script.
Source: https://localizely.com/locale-code/es-419/
Source: https://localizely.com/locale-code/pt-BR/
Source: https://localizely.com/locale-code/zh-Hans
Source: https://localizely.com/language-code/hi/
Source: https://www.unicode.org/iso15924/iso15924-codes.html

### D7. Names that are not translated
`V3RDE` (our app name) and `WhatsApp` (a trademark) stay as they are in every language (`keep` in `languages.json`). The translation step (L4) will protect them.
Source: https://styleguide.dynatrace.com/docs/accessibility-and-inclusivity/internationalization

### D8. The extractor is Go, with no dependencies
The project uses Go where it can. The lexer is small (strings, templates, comments, regex, JSX text check) and needs only the standard library, so the module has no dependencies to download.
Source: https://go.dev/ref/mod#go-mod-file
