# X32e — sources for each decision

Change: X32e, how each app photo was taken, in the ledger. The app sends a small `capture` field with each photo (trigger shutter|barcode, the shot number, source photo|frame|native|upload, ms from the press to the photo, ms to prepare the upload, the preview video's time and state, the track's state); the analyze service logs it as sent (one JSON object, at most 512 bytes) and never uses it for the answer. Decision by T9, 2026-10-27 ("yes we should so a measurement"), after "noticable delay between pressing the camera button and when the shot is taken" and "it will have used an older photo from a previous item". Read 2026-10-27.

Own evidence: the real web export in Chromium with a fake camera sent `{"trigger":"shutter","n":1,"video_t":2.209,"paused":false,"ready":4,"vw":3840,"vh":2160,"track":"live","muted":false,"source":"photo","ms":528,"w":3840,"h":2160,"prep_ms":1191}`; the 9 recorded-answer scenarios of X32b pass with no page errors.

### D61. The preview's state at the press tells a frozen preview from a slow shot
- https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/currentTime — the video's current playback time; it does not move when no new frames arrive.
- https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/muted — a muted track is temporarily unable to provide media data.
- https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/readyState — "live" or "ended".
- https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/readyState — HAVE_CURRENT_DATA (2) and up means a frame can be drawn.

### D62. The ledger keeps the field as sent, bounded, and never acts on it
- https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/ — bound what a client can make the server store: one JSON object, at most 512 bytes, else dropped (`CaptureField`, tested).
