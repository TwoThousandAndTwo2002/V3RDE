### D365. One events line for each management API call, with the AWS answer
- https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-how-to-call-websocket-api-connections.html — the backend sends a message with `POST @connections/{connection_id}` and closes a socket with `DELETE`; the call is signed (SigV4) and needs `execute-api:ManageConnections`. Each call is now a line in the push events (`push.send` for a message, `push.close` for a close): the HTTP status, a code (`forbidden` 403, `gone` 410, `no_answer`, `aws_<status>`), the time of the call (`latency_ms`), what it was for (`pong`, `notify:<kind>`, `close:<why>`), the bytes, and on a failure AWS's reason (the `message` of its answer, up to the first line end, before "The Canonical String", at most 200 bytes: it says which action and which role were refused). A failure is also a log line (`docker logs v3rde-push-1`). A 410 (the socket closed by itself) is normal: a line with `gone`, not a failure. A pong that works (one a minute for each socket) is counted and timed in healthz but is not a line; a pong that fails is. A close has its reason as the code (`session_ended`, `max_age`, `no_ping`, `max_per_user`, `unknown_connection`).
- https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html — log what is needed to find a fault, not more: the connection id is written as the first 12 hex of its sha256 (`conn`), so the lines of one socket can be followed without its id (a network error is written without the URL, which has the id); no secret, ticket, key or cookie is written. A ping with an unknown key (`push.ping` `unknown_key`, at most one line a minute) and each notify (`push.notify`: the sockets of the user, how many got it, the time in all) are lines too.

### D366. Latency and counts in healthz
- https://sre.google/sre-book/monitoring-distributed-systems/ — "the four golden signals": latency, traffic, errors, saturation; latency as percentiles, not a mean. healthz now has `stats`: the sends and how many were 2xx, the count by status, the closes, the pings, pongs and unknown keys, the connects and the refused connects, `latency_ms` (p50, p95 and max of the last 256 calls), and `last_failure` (time, route, status, what, why). The figures start at 0 when the service starts. The push probes (push3–push5) print healthz, so one run shows them.

Review (independent, 15 minutes at most): seven findings, all fixed. (1) A network error's text began with the URL, which has the connection id: the error is unwrapped (`url.Error`). (2) AWS's error body was written raw: now only its message, cut at the first line end and before "The Canonical String" (a signature error repeats the signed request there), with no control characters. (3) A 410 was a failure and would hide a real 403 in `last_failure`: 410 is normal now. (4) The close line of the sweep lost its user and its reason: the close passes the user, its code is the reason (`max_age` apart from `session_ended`), and with push off the line is still written. (5) Pongs of the key path had no user: the key loop reads it. (6) A line for every pong and every unknown key could fill the disk: a pong that works is counted only, and an unknown key is one line a minute. (7) A credentials error was logged twice: once now. The review found the locks, the percentile math and the healthz shape correct.
