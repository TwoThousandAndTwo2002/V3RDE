### D109. One image, one binary per service, every flag in compose "command"
- https://github.com/compose-spec/compose-spec/blob/main/spec.md — "If `entrypoint` is non-null, Compose ignores any default command from the image, for example the `CMD` instruction in the Dockerfile." So each service gives all its flags in `command` (docs/morpheus/post_api.md, X35 shared rules).
- Prior work, `deploy/docker-compose.yml` X21: the sidecars already share one image (`morpheus-telemetry`) with a different `entrypoint`; the post services do the same (`morpheus-post`).

### D110. Memory: a container limit above the Go memory limit
- https://go.dev/doc/gc-guide — for "containers with a fixed amount of available memory", "leave an additional 5-10% of headroom to account for memory sources the Go runtime is unaware of". The image sets `GOMEMLIMIT=200MiB`, so rescue and fan-out get 224m, touch-up 256m, voice 320m (two requests in flight, X36a).
- https://github.com/compose-spec/compose-spec/blob/main/spec.md — `mem_limit` "configures a limit on the amount of memory a container can allocate".

### D111. Caddy: the four app routes with {client_ip}; the internal routes answer 404
- https://caddyserver.com/docs/caddyfile/directives/request_body — `max_size`: "the maximum size in bytes allowed for the request body"; "Reads of more bytes will return an error with HTTP status 413". 64 KB for the JSON routes, 13 MB for one 12 MB WAV.
- Prior work, X31 (`deploy/Caddyfile`): the box is behind a load balancer and Apache, so `{client_ip}` with `trusted_proxies_strict` is the real caller; the post services run with `-trust-forwarded`, so their rate limits key on it.
- Prior work, `server/guard.go`: the analyze token is in the app bundle, so it is public: the bearer routes of the post services (`/v1/touchup`, `/v1/voice`, `/v1/rescue`) and the claim hook (`/v1/fanout/status`, its own secret) have no public route.

### D112. The claim hook: listings tells fan-out after a grab, in the background, with its own secret
- https://www.rfc-editor.org/rfc/rfc9110.html — 409: "the request could not be completed due to a conflict with the current state of the target resource. This code is used in situations where the user might be able to resolve the conflict and resubmit the request": fan-out answers 409 `pending` while the listing is being shared, so the hook retries (2, 5, 10, 20, 40, 60 s = 137 s: longer than the longest share, 10 s photo + 25 s Muse + 60 s upload; an independent review of this change found the first list, 77 s, too short). It also retries on 429, because every claim comes from the listings container and shares one rate-limit key in fan-out. 503: "temporary overload or scheduled maintenance"; fan-out's 503 on this route is `disabled` (no Page), so the hook stops there.
- https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html — "limit shared secrets"; "Using environment variables is therefore not recommended unless the other methods are not possible": a new secret only for listings -> fan-out, a read-only file, made on the box by the stack script (as the analyze token), owner 65534, mode 0600.
- Prior work, handoff A3 item 4: "Only then turn on `-sweep 1m`" — the hook exists now, so fan-out runs with `-sweep 1m`.

### D113. Touch-up's edits are a host folder that listings reads read-only
- Prior work, X32a (`deploy/docker-compose.yml`, listings `-item-photos`): the analyze item photos are a host folder, written by analyze and mounted read-only into listings; the touch-up edits use the same item-photo format (X35a) and the same pattern (`$MORPHEUS_PHOTOS/touchups`), so a listing can take an edit as `photo_id`, owner only.
- https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/ — OWASP API1:2023, how to prevent: "Use the authorization mechanism to check if the logged-in user has access to perform the requested action on the record": listings reads the `user_id` of the edit's record, and one error answers unknown and not-owned.
