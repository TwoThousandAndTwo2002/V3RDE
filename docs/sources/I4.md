### D328. The chat's mapping names the missed item; the app does not add it
- https://genai.owasp.org/llmrisk/llm01-prompt-injection/ — the transcript stays data. The model's `find` is only a list of names: each is cleaned to a short noun phrase (the find service's rule, `findName`), at most 3, and the app sends each to the find service, which looks in the photo. "Voice cannot add food that the photo does not show" stays true: no item is added from words alone (`new_items` stays empty in edit mode).
- A name that is already a title of the list is not a missed item (it is left out and logged in `dropped`). With no scan (a voice-only draft) `find` is refused: there is no photo to look in.

### D329. The answer of each find in the chat; Post waits
- https://www.w3.org/WAI/WCAG21/Understanding/status-messages.html — the chat thread is a polite live region, so "Looking for rice in the photo…" and the result are read out without moving the focus.
- Post already waits while a chat line is out (X48s); it also waits while a find is out, so a found item cannot come after the post.

### D330. Found items join the list
- https://react.dev/reference/react/useRef — a ref changes at once and keeps its value across renders (state changes only at the next render). The highest item number used so far (`top`) and the list as it is now (`current`) are refs, so two finds that end close together, or a chat line that ends right after a find, never reuse a number or read an old list.
- The item numbers go on after the highest of the scan and of the list (`joinFound`): a number of a removed item is never used again, so the label report and the card marks stay right. "Found from your words" uses the `link` colour of the chat marks (X48s).
- A one-item review shows the form; with a found item it becomes the list (the form shows one item only).
