# L2 — sources for each decision

Change: L2 on branch `LIF`. The quality-estimator image (`qe/Dockerfile`) rebuilds from the cache: a change to one pin or to our own code no longer builds and downloads everything again. The apply script prints, for each build step, whether it came from the cache. The scores and the smoke test are the same as in L1.

### D1. A BuildKit cache mount for pip, and no --no-cache-dir

In L1 every change to a pin rebuilt the whole pip layer and downloaded torch again. With `RUN --mount=type=cache,target=/root/.cache/pip`, pip's download cache stays between builds, also when the layer itself is rebuilt, so only a changed package is downloaded. `--no-cache-dir` is removed, because it would leave that cache empty.

- https://docs.docker.com/build/cache/optimize/
- https://www.freecodecamp.org/news/how-to-optimize-your-docker-build-cache/

### D2. Layers from the least often changed to the most often changed; torch in its own layer

A changed layer invalidates every layer after it. So the order is: apt, the pinned MetricX clone, torch (the largest download, which seldom changes), MetricX's requirements with the small pins, and our own code (`run_predict.py`) last. The first build after L2 is a full build once, because the instructions changed; after that, the cache applies.

- https://docs.docker.com/build/cache/optimize/
- https://oneuptime.com/blog/post/2026-02-08-how-to-order-dockerfile-instructions-for-optimal-caching/markdown

### D3. A cache mount for apt, with the Debian clean-up hook removed

The apt step uses cache mounts for `/var/cache/apt` and `/var/lib/apt` with `sharing=locked`. The Debian base image has a hook (`docker-clean`) that deletes downloaded packages after each install, which would leave the cache empty; the Dockerfile frontend documentation removes it and keeps the downloads in the same way. A `# syntax=docker/dockerfile:1` line selects a Dockerfile version that supports `RUN --mount`.

- https://hub.docker.com/r/docker/dockerfile
- https://docs.docker.com/build/cache/optimize/

### D4. The apply script shows the cache result of every build step

The image is built with `--progress=plain`, and the script prints each Dockerfile step as `CACHED` or `rebuilt`, so every run shows what came from the cache. `qe/test_qe.py` has a new regression test that keeps the cache mounts, the removed `--no-cache-dir` and the layer order in place.

- https://oneuptime.com/blog/post/2026-02-08-how-to-order-dockerfile-instructions-for-optimal-caching/markdown
