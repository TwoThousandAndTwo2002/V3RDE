### D155. One call for every item photo of one answer
- https://bunny.net/blog/why-optimizing-your-images-with-base64-is-almost-always-a-bad-idea — base64 makes an image "more than 25%" larger and the browser cannot cache it; separate files over HTTP/2 are the usual way. T9 chose JSON + base64 for now (one call, the crops are shown one time); separate URLs over HTTP/2 are the later step.
- The answer keeps the order of `photo_ids`; each item has its size, JPEG quality, sha256 and `jpeg_base64` (for `data:image/jpeg;base64,...`). 24 crops at 40 KB are about 1.3 MB with base64.

### D156. Each photo must be the caller's AND of that answer
- https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/ — "check if the logged-in user has access to perform the requested action on the record."
- Each id's record is read with the owner check of `ReadItem`, and it must have the asked `request_id`. One failed id gives 404 for the whole call, with the same answer for an unknown id, another user's id and another answer's id. The check runs before the cache and before any photo is read.

### D157. Small images in a bounded pool, with a size target
- `go doc image/jpeg Options` (Go 1.24.7): "Quality ranges from 1 to 100 inclusive, higher is better." The quality is found by a binary search on 30–95 (at most 7 encodes: the highest quality that fits, and the next one does not); if even 30 is over the target, 30 is kept and the real size is given.
- A "full" item photo is the upload as it was, so any upload type is decoded (JPEG, PNG, GIF, WebP) and turned upright by its EXIF orientation (the crops already are). An image over 50 million pixels is not decoded (the gate's limit).
- `golang.org/x/image/draw` v0.36.0 (`draw/scale.go`): "CatmullRom ... is very slow, but usually gives very high quality results." The long side is scaled to 282 or 800 px, never up.
- One pool of `runtime.NumCPU()` workers for ALL bundle calls together, and at most 2 calls at the same time (a third gets 503 `busy`); each worker reads its own photo, so at most NumCPU photos are in memory; 20 s per call (504 `timeout`), under the API Gateway limit of 30 s (https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-quotas.html).
- With the default target (40 KB) each small photo is kept (`items/small/<photo_id>_<side>.json`, at most 2 files per photo), because the crops never change; a call that is all in this cache needs no slot. Other targets are made each time.

### D158. One event per call, with no image bytes
- https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/ — the event keeps the caller and the user, so every read of a photo can be traced.
- Step `photos_bundle`: the analyze `request_id`, the count, side, kb, bytes in and out, the read and compress time, the workers, the cache, and each item's quality. A test checks that the event holds no image bytes.
