### D292. A barcode hit's listing photo is the stock photo: the cutout, else the photo as is; else the camera shot
- https://vn.openfoodfacts.org/terms-of-use — "Products images are available under the Creative Commons Attribution ShareAlike licence." So the photos can be used in the app, with the attribution of D294.
- The barcode service answers the product's `gtin14` (`barcode/handler.go`, `Response.GTIN14`); the photo files are named by it. Only 14 digits are read (no path from the request), at most 1 MB, and only a JPEG.
- The photo is saved as an item photo of the caller (kind `stock`), so the review, the listing and the touch-up routes use it with the same owner check as before (https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/). The camera shot is still stored under its sha256 (training data, X32a).
- No photo for the product, or the folder empty or not mounted: the camera shot, as before. The events line has `stock_photo` (cutout, as_is, none, or unreadable: a file that is there but cannot be read, is not a JPEG, or is too large; review). If the stock photo cannot be saved, the camera shot is used and the events line has the error (review).

### D293. Only the app's session route; the bearer route does not change
- https://docs.github.com/en/rest/overview/breaking-changes — the list of breaking changes names "Removing or renaming a response field" and "Changing the type of a parameter or response field"; a new optional field is not in it. So `photo_credit` is only added, and only when there is a stock photo.
- `/v1/analyze` (the bearer token) is the route of the team's app, and the earlier rule keeps it unchanged (Icarus handoff, 2026-10-28: "`/v1/analyze` unchanged"). Its answers and its photo stay the same (test). The app's own route `/api/analyze` (session cookie) gets the stock photo.

### D294. The answer and the listing carry the credit; the app interface does not change now
- https://vn.openfoodfacts.org/terms-of-use — re-users "have to mention the licence and to attribute the authorship to Open Food Facts"; "Such attribution is also necessary for derivative works."
- So the answer item and the listing have `photo_credit` "Open Food Facts, CC BY-SA" (left out for the user's own photo; the JSON of the other answers does not change). A touch-up of the caller's own stock item photo is a derivative work, so its listing keeps the credit (review: the touch-up record names its `source_photo_id`). T9 (2026-10-31): no interface change in this change, so the app does not show it yet; a client can show it from these fields.

### D295. The photos are a read-only folder on the box, mounted into analyze
- https://docs.docker.com/engine/storage/bind-mounts.md — "You can use the `readonly` or `ro` option to prevent the container from writing to the mount"; with `-v` (the compose short form) and a host path that does not exist, "Docker automatically creates the directory on the host for you" (empty), so the deploy before the photos are copied works and gives the camera shot. The copy job runs as root, swaps the folder whole, and makes every file readable (`a+rX`), so the container user can read it (review).
- The copy to the box goes by a temporary branch, deleted after the copy (the X31b path), in tar parts of at most 90 MB: https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github — "GitHub blocks files larger than 100 MiB."
