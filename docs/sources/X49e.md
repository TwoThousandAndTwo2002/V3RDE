T9 (2026-10-30) asked what happens when a user grabs an item and is not in the area. The code then had no place at all: the list showed every active item, the grab had no distance check, and a grab could not be given back. T9 chose fix D (A + B + C) and approved the "V3RDE Distance Mockup" (version 2): the place of an item is the giver's phone location, or a ZIP code when location is off; the receiver's place is the phone location, or a ZIP code; the receiver picks 1, 5 or 10 mi; "items further away show up but are grayed out with a distance on them"; a far grab = farther than the user's pick ("if its more then the preset the choose then its a far grab"); release "until the timer ends"; the place is kept to ".01 mi"; the gray part goes to "25 miles".

Own evidence: cloud tests (listings 31 -> 42, post 67 -> 68, mobile 108 -> 118), and a run of the real app (web export) against the real listings service in a browser with a set location: the place popup, 5 mi then 1 mi, the gray part, the far check, grab, "Your pickup", release, a refused location (the ZIP popup), a bad and a good ZIP, and the desktop layout. ### D260. The place of a listing is stored rounded to 0.01 mi, and only the distance leaves the server
- T9: "lets do .01 mi". The stored point is snapped to a grid of 0.01 mi (latitude steps of 0.01 mi; longitude steps that are 0.01 mi long at that latitude), so it moves at most 0.0071 mi. The list answer has `distance_mi` rounded to 0.1 mi (the app shows one decimal), never the point. Independent review: with 0.01 mi, three requests from made-up places would find the giver's point (trilateration), so the answer is coarser than the stored point.
- https://en.wikipedia.org/wiki/Haversine_formula — the great-circle distance on a sphere (numerically good for short distances).
- https://en.wikipedia.org/wiki/Earth_radius#Arithmetic_mean_radius — the IUGG mean radius 6371.0088 km; https://en.wikipedia.org/wiki/Mile — 1 international mile = 1609.344 m exactly (the mile of the app's "mi").

### D261. A ZIP code is the internal point of its ZCTA (US Census 2024 Gazetteer)
- https://www.census.gov/programs-surveys/geography/technical-documentation/records-layout/gaz-record-layouts.2024.html — the 2024 Gazetteer ZCTA file: GEOID and INTPTLAT/INTPTLONG (the internal point) for each ZIP Code Tabulation Area; https://www2.census.gov/geo/docs/maps-data/data/gazetteer/2024_Gazetteer/2024_Gaz_zcta_national.zip (sha256 7b85c04a131672f58b38a950eb82855d5fd4054f0bd9bc3f69aa28897a714e3d, 33,791 ZCTAs). A ZCTA is close to a USPS ZIP code, not the same (https://www.census.gov/programs-surveys/geography/guidance/geo-areas/zctas.html); a ZIP with no ZCTA (a PO box ZIP) is refused with "unknown zip code".
- `cmd/zctatable` makes `listings/zcta.csv` from that zip (the sha256 is pinned), and the service embeds it (https://pkg.go.dev/embed).
- Census Bureau open data: https://census.gov/about/policies/open-gov/open-data.html (US government work, https://www.copyright.gov/title17/92chap1.html#105).

### D262. The receiver's place is sent with each request and never stored
- The list (`GET /api/listings?lat=&lng=` or `?zip=`) and "Your pickup" (`GET /api/listings/grabbed`) take the place as query values; the service does not keep it. The app keeps only the choice (location or a ZIP, and 1/5/10 mi) on the device.
- https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/getCurrentPosition — the browser asks the user; error code 1 is PERMISSION_DENIED (then the ZIP popup); `enableHighAccuracy: false` (a city-block place is enough for 1 mi) and `maximumAge` 60 s.
- https://developer.mozilla.org/en-US/docs/Web/API/Geolocation_API#security_considerations — the location works only in a secure context (the box is served over https).
- A phone build has no location module yet (it would need expo-location and a new EAS build): there the app asks for the ZIP code.

### D263. Food farther than the pick shows in gray, up to 25 mi, nearest first; a grab of it asks first
- T9's choices (above). The gray is the existing `opacity.gone` token, so no new token. The list is sorted by distance on the server (then newest first), so the near part always comes before the gray part, also across pages; the page cursor is the count of listings on the pages before.
- https://m3.material.io/components/dialogs/guidelines — a dialog for a decision that needs the user's attention before it goes on (the far grab takes the food from everyone else).

### D264. A grab can be released until the timer ends; the listing is active again with the same timer
- T9: "yes until the timer ends". Only the user who grabbed it (409 otherwise); after the timer, 409 "listing expired". The listing keeps its expires_at.
- Fan-out removes "[CLAIMED]" (status "released"); the calls of one listing go to fan-out in the order of the store changes: the call is queued while the store is locked (independent review: queued after the unlock, a grab by B right after A's release could end with no [CLAIMED]), and each call waits for the one before (https://go.dev/ref/mem — a channel close happens before the receive that sees it). The HTTP answer does not wait.
- Independent review: the next page starts after the key (distance, created_at, id) of the last listing shown, not after a count, so a grab between two pages does not make the list skip a listing. The key holds the shown distance (0.1 mi), never the exact one (re-check).

### D265. A new listing needs a place
- The app always sends one; a create without lat and lng or a zip is 400 "send lat and lng, or a 5-digit US zip". Listings from before this change have no place: they are not in a place list (they expire 30 minutes after they were made).
- https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/400 — a request the server cannot take because of the client's input.
