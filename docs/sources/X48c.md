# X48c — sources for each decision

Change: X48c, the held poll of a scan job (`inference/scanjob.go`, `inference/service.go`, `mobile/src/logic.ts`, `mobile/src/api.ts`; NEW_WORK.md 50). Speed plan item: the app asked once a second, so each step of a scan (and the answer) reached the app up to 1 s late; the app slept 1 s before the first ask too.

Own evidence (2026-10-29, cloud tests): `TestScanJobHold` (a held poll answers in under 2 s when the stage changes 50 ms later; an old version and an ended job answer at once; no change ends at the hold time; the hold ends when the caller goes away), `TestAnalyzeAsyncHeldPoll` (the app's loop with since + wait reaches the answer, the version never goes down; a bad wait is not held). Inference tests 84 -> 86, mobile 81 -> 82; the race run is clean.

### D202. A held poll (long polling), not a stream
- https://datatracker.ietf.org/doc/html/rfc6202 — section 2.1: long polling "attempts to minimize both the latency in server-client message delivery"; the server answers "only when a particular event, status, or timeout has occurred."
- The public name stays an API Gateway HTTP API with no stream (docs/sources/X44b.md). A held poll is a normal short request, so nothing changes at API Gateway, Apache or the edge.
- The job has a `version` that goes up at each change (stage, boxes, a name, the end). The app sends `since=<the version it has>`: a change that came between two polls is never lost, because a different version answers at once.
- Old and new parts work together: an old service ignores `since` and `wait` (it answers at once, with no version), and the app then waits 1 s as before.

### D203. The hold is 8 s (the service caps it at 10 s)
- https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-quotas.html — "Maximum integration timeout | 30 seconds | No".
- https://datatracker.ietf.org/doc/html/rfc6202 — section 5.5: "generally 30 seconds is a safer value" because proxies and servers have shorter timeouts. The hold is far under that and under the 30 s of API Gateway; the app's own request time limit is 18 s.
- With 8 s, a scan of 10-25 s needs few polls; `stop` (the user went back) is seen at the next answer, at most 8 s later; the job then ends on its own.
